## 追查：为什么 403 没触发自动禁用 key（已定位根因）

结论链路（本地 custom 分支代码 + 线上 options 配置双向验证）：

1. braintrust 的 403 响应是**纯文本、无 Content-Type**，body 为
   `Braintrust gateway error: ... insufficient credit balance`。
2. `service/error.go: RelayErrorHandler` 对 body 做 `common.Unmarshal` 失败；
   所有 relay handler 调用时 `showBodyWhenFail=false`（只有 channel-test.go:445 传 true），
   于是走 error.go:110 分支，错误消息被简化成 **`bad response status code 403`**，
   上游真实原因被丢弃。线上日志 content 正是 `status_code=403, bad response status code 403`，已印证。
3. `service/channel.go:62 ShouldDisableChannel` 三条路径全部落空 -> 返回 false：
   - 状态码：`setting/operation_setting/status_code_ranges.go:17`
     `AutomaticDisableStatusCodeRanges` 默认 `[]{{401,401}}` —— **只含 401，不含 403**；
     线上 options 未覆盖此 key，故为默认值。
   - 关键词：匹配前 `strings.ToLower(err.Error())`，dict 也在 `service/str.go:readRunes`
     里 ToLower（所以大小写不是问题），"INSUFFICIENT" 本可命中——
     但消息里已经没有 "insufficient" 了。
   - 渠道错误：403 是上游有响应的业务错误，不算 ChannelError（5xx/网络类才算）。
4. `controller/relay.go:383 processChannelError` 因此不进入禁用分支。
   注意：多 key 场景下禁用粒度是**按 key**（`service.DisableChannel` ->
   `model.DisableChannelKeyUntil(channelId, usingKey, ...)`），机制本身是正确的。

对照验证：10845 vyceai 同为余额不足(402)但响应是 JSON、消息被完整保留为
`Insufficient balance. Please top up your account.`，命中关键词 insufficient
-> 2 个 key 全被禁用且渠道 status=3。说明关键词路径有效，差别只在消息是否保留。
另 10836(633 禁用)/10831(45)/10821(279) 的触发错误码是 500/400，走的是 IsChannelError 路径。

止血 API：`POST /api/channel/multi_key/manage`，body 带
`{"action":"disable_key","channel_id":10844,"key_index":N}`（路由见 router/channel-router.go:74，
状态值 2=disabled；注意线上二进制里 GetNextEnabledKey 的语义是"不在 status_list 中即视为启用"）。

## 实施：治本修复（已改代码，未构建部署）

问题：非 JSON 的上游错误响应导致 `RelayErrorHandler` 把消息退化成
`bad response status code N`，真实原因丢失，`AutomaticDisableKeywords` 全程失效。

改动（4 个文件，编译 + 单测 + 回归全绿）：
1. `types/error.go`：NewAPIError 增加**未导出**字段 `upstreamBody`（不会被 JSON 序列化，
   不会进客户端响应，也不会进 logs 表）；新增 `ErrOptionWithUpstreamBody(body)` 与
   `(*NewAPIError).UpstreamBody()`。
2. `service/error.go`：新增 `upstreamBodyKeywordLimit = 4096` 与 `truncateUpstreamBody()`；
   `RelayErrorHandler` 在读完 body 后注册 defer，无论走哪个分支都挂上截断后的原文。
   用 defer + 命名返回值，自动覆盖所有 return 路径（含 `newApiErr` 被重新赋值的分支）。
3. `service/channel.go`：`ShouldDisableChannel` 关键词匹配先查 `err.Error()`，
   未命中再查 `err.UpstreamBody()`。
4. `service/error_test.go`：新增 3 个测试（保留/截断/关键词匹配三分支）。

验证：用线上真实 `AutomaticDisableKeywords` + braintrust 真实 403 文本跑通，
对外消息仍是 `bad response status code 403`（不泄露 body），`ShouldDisableChannel` 返回 true。
完整主程序 build 通过（156MB 产物验证后已删），gofmt 干净。

已提交并推送：`dd0c86c27 fix(channel): match auto-disable keywords against upstream body`（custom 分支）。

## 补记：真正的根因是两层（前面分析有一处误判）

**教训：查 options 表千万别用 `left(value, N)` 截断。** 我第一次查 AutomaticDisableKeywords
用了 `left(value,300)`，而实际长度 329，把末尾的 `INSUFFICIENT_BALANCE` 截成了 `INSUFFICIENT`，
导致我误判"配置里有 INSUFFICIENT 这个词、关键词本该命中"。

实际关键词末尾两项是 `INSUFFICIENT_BALANCE` 和 `insufficient balance`，
而 braintrust 的原文是 **`insufficient credit balance`**（中间多了 credit）——两者都不匹配。

所以这个问题是**两层原因叠加**，只改代码不够：
1. 代码层：非 JSON 响应退化成 `bad response status code 403`，真实原因丢失（已修，必须）；
2. 配置层：现有关键词措辞与上游不匹配（补 `insufficient credit`，已加）。

改配置的方法：直接 UPDATE options 表即可，`main.go` 里 `go model.SyncOptions(common.SyncFrequency)`
每 60 秒从 DB 热加载（`common.SyncFrequency` 默认 60），无需重启。
备份：服务器 `/tmp/keywords_backup_20260914_1955.txt`。

**结果**：21 个坏 key 全部被自动禁用，索引恰好是 0..20，与首轮 curl 检测结果完全吻合；
保留 21/22/23 三个好 key，渠道状态保持 1。发 8 个请求验证 7 成功，
唯一一次失败是 402 "Activate your plan to continue"（调用方 token 余额不足，与渠道无关）。

**全局影响复查**（部署后 45 分钟）：除 10844（0 -> 21）外，所有渠道的 status 和
multi_key_status_list 条目数与基线完全一致，无任何误伤。10838 b.ai 的 key 总数
6904 -> 7047 是运营加 key，禁用数仍为 0。说明新增的 `insufficient credit` 关键词安全。

**验证技巧**：改完等生效时，如果渠道正好没流量（日志停更），看不出效果。
可在服务器上用 DB 里的 token 打 `http://127.0.0.1:3000/v1/chat/completions`（宿主映射端口）

## y-api 分组「每日 500 次」限流核查

限制走的是**通用「模型请求限流」中间件**（`middleware/model-rate-limit.go`），不是分组专属功能。
线上 options：

- `ModelRequestRateLimitEnabled = true`
- `ModelRequestRateLimitDurationMinutes = 1440`（1440 分钟 = 一天）
- `ModelRequestRateLimitGroup = {"y-api": [600, 500]}` → 数组含义 `[总请求上限, 成功请求上限]`
- 全局 `ModelRequestRateLimitSuccessCount = 0`、`ModelRequestRateLimitCount` 无该行（默认 0）
  → 只有 y-api 分组被限，其他分组不受影响。

判定逻辑（`redisRateLimitHandler`）：取 token 分组优先、否则用户分组（`GetGroupRateLimit`），
两条路径：①成功计数用 Redis LIST `rateLimit:MRRLS:<userId>`，`LLEN < 500` 才放行，
且只在响应 <400 时才 LPUSH 记录；②总计数用令牌桶 hash `rateLimit:<userId>`
（capacity=600*86400、rate=600/s、每请求消耗 86400），**注意 `if !allowed` 分支缺少 return**，
abort 后仍会继续 `c.Next()`。

查线上状态的方法（Redis 需密码 `Yt0uR3dis_2026!`，容器 `new-api-redis`，Redis 已启用）：

```bash
# 1. 取 y-api 分组用户 id
ssh yutou-prod 'docker exec new-api-postgres psql -U newapi -d newapi -t -A -c "select id from users where \"group\"='"'"'y-api'"'"' order by id" > /tmp/yapi_ids.txt'
# 2. 批量 LLEN（用管道喂命令，避免 1048 次 docker exec）
ssh yutou-prod '{ while read id; do echo "LLEN rateLimit:MRRLS:$id"; done < /tmp/yapi_ids.txt; } | docker exec -i new-api-redis redis-cli -a "Yt0uR3dis_2026!" --no-auth-warning > /tmp/yapi_lens.txt'
```

本次结果（2026-09-14 20:20）：y-api 分组共 1048 人，**8 人被限**：

- 7 人成功计数顶满 500（345/501/694/735/977/1010/1244），全部是 `ya-*` 前缀的机器账号；
  LLEN 上限就是 500（LTrim 截断），解禁时间 = 最老一条记录满 24h，
  按最老时间戳推算均在**次日 13:03–15:04（GMT+8）**左右陆续恢复。
- 1 人（338）撞的是**总请求 600 上限**：令牌桶 tokens 62400 < 86400，
  且其 MRRLS 长度为 0（请求全失败、无成功记录），属于失败请求刷量。
- 分布：0 次 914 人、1–99 次 114 人、100–399 次 13 人、400–499 次 0 人、满 500 共 7 人。
  次高的是 1338(269)、327(254)、533(210)，离上限还有距离。

日志验证：`docker logs new-api --since 24h | grep '已达到'`，近 24h 共 71 条拒绝，
其中 1010 33 条、338 32 条、501 6 条；消息形如
`您已达到请求数限制：1440分钟内最多请求500次` / `您已达到总请求数限制：1440分钟内最多请求600次`。
（`middleware/rate-limit.go` 里 `timeFormat = "2006-01-02T15:04:05.000Z"` 的 `Z` 是字面量，
写入的是容器本地时间 GMT+8，读取时同样按此解析，差值不受影响。）

**触限时的对外响应**：`middleware/utils.go:abortWithOpenAiMessage`，HTTP 429，
body 为 `{"error":{"message":"<msg> (request id: <id>)","type":"new_api_error","code":""}}`
（`code` 恒为空串，因为限流分支没传 ErrorCode；`type` 不是 OpenAI 标准的
`rate_limit_exceeded`）。消息文案两条：
`您已达到请求数限制：1440分钟内最多请求500次`（成功额度）、
`您已达到总请求数限制：1440分钟内最多请求600次，包括失败次数，请检查您的请求是否正确`（总额度）。
Redis 检查异常走 500 + `rate_limit_check_failed`；非 Redis（内存限流）模式只返回裸 429、无 body。
