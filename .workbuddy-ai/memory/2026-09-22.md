付费模型无 key → 401 `PAID_MODEL_AUTH_REQUIRED`；余额 0 → 402；组织可配 per-user 日限额（UTC 午夜重置）。

- **带无效 key + 免费模型 → 401 `INVALID_TOKEN`** ⚠️ 反直觉：要匿名白嫖就**别带 Authorization 头**。

## 渠道 10859（modelscope）`/v1/messages` 流式「无输出」——定位到两个独立 bug

**现象**：用户 1394（`ya-m487w6h4hewjvvpp`，group `y-api-paid`）从 22:46 起打 10859，
流式请求 `completion_tokens` 恒为 0（22 条全 0），非流式正常（334 / 3861）。

**根因 A（客户端可见的"无输出"）——Claude 转换丢弃同一 chunk 里的 `content`**：
`service/relayconvert/internal/oai_chat/to_claude_messages_resp.go`
- 首块分支 L192-238：`if reasoning != "" {…} else if content != "" {…}`
- 常规分支 L362-398：`if reasoning != "" {…} else {content…}`
ModelScope 的 DeepSeek-V4.1-Flash **把最后一个 `content` 和 `reasoning_content` 放在同一个 SSE chunk 里**
（实测 `"delta":{"content":"PONG","reasoning_content":" with that."}`）→ 走 reasoning 分支，
`content` **被静默丢掉** → 客户端只收到 `thinking` 块，**永远没有 `text` 块** → Claude 类客户端显示无输出。
端到端复现（生产 new-api + 临时令牌）：`/v1/messages` 只出 `thinking_delta`，`/v1/chat/completions`
同渠道同模型正常出 `content:"PONG"`。修法：两个分支都要「先发 thinking_delta，再关 thinking 块、
开 text 块发 text_delta」。

**根因 B（日志/计费侧，会让"有输出"也记成 0）——`/v1/messages` 的 RelayMode 是 Unknown**：
`relay/common/relay_info.go:487` 用 `Path2RelayMode(c.Request.URL.Path)`，而
`relay/constant/relay_mode.go:57-93` **没有 `/v1/messages` 分支** → 返回 `RelayModeUnknown(0)`
（自检日志里可见 `RelayMode: 0`）。于是 `relay/channel/openai/helper.go:110` 的 `processTokenData`
switch 一个都不匹配 → `responseTextBuilder` 恒空 → 上游没回 usage 时 `ResponseText2Usage` 算出
completion=0（`local_count_tokens: true` / `usage_billing_path: local`）。**输出 token 不计费**。
修法：`processTokenData` 的 case 加 `relayconstant.RelayModeUnknown`（OpenAI 兼容上游的响应恒为 chat 形态）。

**影响面**：近 7 天「`/v1/messages` + 流式 + local 计费」共 666 条、**8 个渠道全部 completion=0**
（10850/10831/10844/10859/10838/10852/10851/10856）。根因 B 是全局的；根因 A 只在
上游把 content 与 reasoning 同 chunk 下发时触发。

**排查手法（可复用）**：① `logs` 按 `request_path` × `is_stream` × `completion_tokens=0` 分组；
② `docker logs new-api | grep 'testing channel #<id>'` —— **渠道自检会把原始响应体打印出来**，
是看客户端到底收到什么的最快手段（`GET /api/channel/test/<id>?model=<m>&endpoint_type=anthropic&stream=true`）；
③ 同一渠道对比 `/v1/messages` vs `/v1/chat/completions`，能一眼区分「上游问题」和「转换层问题」。
④ ⚠️ 临时令牌改 group 后**令牌有缓存**，立刻发请求会沿用旧 group（报"无权访问 X 分组"），等一会儿再试。

**绕开方案已验证（改渠道类型，不改代码）**：ModelScope **有 Anthropic 原生端点**
`https://api-inference.modelscope.ai/v1/messages`（`x-api-key` 和 `Bearer` 都收，`/anthropic/v1/messages` 是 404）。
把 10859 从 type 8 改成 **type 58 + `base_url` 只写前缀 `https://api-inference.modelscope.ai`**，
配路由 `{incoming_path:/v1/messages, upstream_path:/v1/messages, converter:none}` +
`{incoming_path:/v1/chat/completions, upstream_path:/v1/chat/completions, converter:none}`，
走 `advancedcustom.doNativeResponse` → `claudeAdaptor` 原生透传，**两个根因同时消失**。

实测对照（建临时禁用渠道 10860 验证，测完已删；`converter:none` 未匹配路径会报
`advanced custom channel does not support request path X`，所以要覆盖全部在用的 path）：

| 配置 | `/v1/messages` 流式 | 日志 |
|---|---|---|
| type 8（base_url=完整 `/v1/chat/completions`） | 只有 `thinking_delta`，**无 `text_delta`** | pt=17 ct=0 `local_count_tokens:true` `local` |
| type 58 + `converter:none` 原生路由 | `text_delta:"PONG"` **正常** | pt=38 ct=35 `usage_billing_path:billing-usage-anthropic` |

但**只修 10859 一个渠道**，两个代码 bug 仍在（另 7 个 OpenAI 兼容渠道同样会丢 content；

`request_conversion` 由 `["Claude Messages","OpenAI Compatible"]` 变为 `["Claude Messages"]`。**主问题（无输出）已修复。**

**遗留现象**：用户 1394 的 **~64 万 token** 流式请求 4 次只成 1 次
（`scanner_error/unexpected EOF` ×1、`client_gone` ×2、成功 ct=95 ×1）。

**归因（已验证，非本次变更引入）**：
- **pre-change 的 `frt` 就已经是 34s–122s**，且 23:16 那条也是 `client_gone`（`frt=-1000`＝首字节都没等到）
  ⇒ 长等待是**上游固有**的，不是改渠道类型造成的。对比渠道 10844/10856 处理 48–54 万 token 时
  `frt` 只有 17–32s，说明**是 ModelScope 慢**，不是网关慢。
- **直连两端点实测（从生产服务器，同一份 640k prompt）**：
  | 端点 | 首字节 | 行为 |
  |---|---|---|
  | `/v1/messages` | 2.9–11.4s | 立刻发 `message_start`+`content_block_start`+`event: ping`，**然后整段静默**；3 次里 max_gap 分别 81.1s / 34.7s / 8.0s，之后才吐 `content_block_delta` |
  | `/v1/chat/completions` | **103.3s** | 静默 103s 后**一次性吐出全部 36 行**（max_gap=0.2s），本质是「攒完再发」 |
  ⇒ **失败模式变化的原因**：OpenAI 端点只在「响应前」静默（无中途空档），所以从不触发
  `scanner_error`；原生 Anthropic 端点是真的流式，中途有 30–120s 空档，于是会被客户端/中间层掐。
- **`ping_interval_enabled` 平台级关闭**：`setting/operation_setting/general_setting.go:28` 默认 `false`，
  `options` 表里**没有** `general_setting.ping_interval_enabled` 行，且 `config.LoadFromDB`
  只覆盖已存在的键 ⇒ **生产环境从不给下游发保活**。这是 `client_gone`（客户端/前置 nginx 在空档期超时）
  的直接原因，且**影响全平台**（不止 10859）。
- 另：`stream_scanner.go` 的 `event:` 行被丢弃、只透传 `data:`，所以上游那个 `{"type":"ping"}` 会变成
  裸 `data: {"type":"ping"}` 发给客户端——首字节有动静，之后仍无保活。
- 偶发**上游提前断流**：另一次直连实测 `/v1/messages` 只回 9 行（`message_start`+`content_block_start`+`ping`）
  就结束，无 `content_block_delta`/`message_stop` —— 对应网关侧的 `received=3` + `unexpected EOF`。

**建议（未执行，属全局配置，需用户决定）**：打开 `general_setting.ping_interval_enabled=true`
（间隔 15–30s），可同时缓解 10844/10856 等所有「大 prompt 长静默」渠道的 `client_gone`。
⚠️ 这是**全平台设置**，不符合用户「只改 10859 渠道」的约束，故只报不改。
