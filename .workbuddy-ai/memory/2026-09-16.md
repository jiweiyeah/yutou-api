## 19:10 查清渠道 priority / weight 的真实语义

起因：问「渠道里优先级和权重是什么意思」，顺手核对了代码路径与线上开关。

**关键发现：线上根本没开内存缓存。** `common/init.go:86` 只认 env
`MEMORY_CACHE_ENABLED == "true"`；`docker inspect new-api` 的 Config.Env 里**没有这个变量**
→ `common.MemoryCacheEnabled = false` → 选渠道走 **DB 路径 `model.GetChannel`**
（`model/ability.go:108`），`model/channel_cache.go:116` 那套内存缓存逻辑线上不生效。

两条路径的权重算法**语义不同**，这是之前没注意到的：

| | DB 路径（线上） | 内存缓存路径 |
|---|---|---|
| 公式 | `Σ(weight+10)`，每档扣 `weight+10` | 全 0 时按 100 算；否则 `weight*factor` |
| weight=0 | **仍有 10 的保底份额** | 同档有正权重渠道时**拿不到流量** |

→ 线上实际份额 = `(weight+10) / Σ(weight_i+10)`。想要 8:2，得设 weight 70 / 10，不是 80/20。

其余结论：
- priority 是**主备降级**语义：`getChannelQuery` 只取 `priority = MAX(priority)` 那一档；
  `getPriority` 按 priority DESC 取第 retry 个；retry 超档数时夹到最低档（低优先级会被反复打）。
- 改 priority/weight 后 controller 会调 `model.InitChannelCache()`，但线上不依赖缓存，
  **改动基本立即生效**，不用等 60s 同步窗口（旧备忘里那条只适用于缓存路径）。
- 前端文案：priority「优先级更高的渠道优先被选中」；weight「用于负载均衡。权重越高 = 请求越多」。

已把这节写进 MEMORY.md。

## 19:20 追问：模型不同时的优先级影响 + 权重 1/0 的实际比例

两个问题都做了代码核对 + 数值模拟（脚本 `/tmp/chsim/sim.py`，40 万次）。

**Q1 两个渠道模型不一样，设不同优先级会不会让低优先级调用不了？**
答：**看模型有没有交集**。候选集是按 `(group, model)` 切分的
（`abilities` 主键 = group + model + channel_id；`AddAbilities` 遍历 models × groups 生成行）。
- 模型完全不重叠 → 互不影响，低优先级渠道照常服务（它自己那个模型的 `MAX(priority)` 就是它）。
- 有交集 → 交集模型上高优先级独占，低优先级零流量（除非高优先级整档失败触发重试降级）。
- 附带结论：priority 是**渠道级**字段，不能给同一渠道的不同模型设不同优先级。

线上实测：`select priority, count(*) from abilities where enabled group by priority`
→ `0|55|18`，**55 条 ability 的 priority 全是 0**，也没有任何模型存在多档优先级。
优先级这个功能线上目前完全没用起来。

**Q2 权重 1 和 0 的流量比例？**
答：线上 DB 路径下 **57.3% : 42.7%**，几乎对半。原因：公式是每渠道 `w + 10` 保底，
且判定是 `weight <= 0`（不是 `< 0`），排在前面的渠道再多算 1 份 →
精确份额 `(wA+11) / (wA+wB+20)`。1/0 → 12/21 = 57.14%，与模拟吻合。

实测对照（DB 路径 / 内存缓存路径）：
| 权重 | DB（线上） | 缓存路径 |
|---|---|---|
| 1 : 0 | 57.3 : 42.7 | 100 : 0 |
| 0 : 0 | 55.0 : 45.0 | 50 : 50 |
| 80 : 20 | 75.8 : 24.2 | 80.1 : 19.9 |
| 70 : 10 | 81.1 : 18.9 | 87.5 : 12.5 |
| 100 : 100 | 50.4 : 49.6 | 50.1 : 49.9 |

→ 实用结论：**权重必须设到几十以上，比例才符合直觉**；个位数权重会被 +10 保底严重稀释。
想要精确 8:2，设 25 : 0（(25+11)/45 = 80%）。想让某渠道彻底不出流量，只能禁用或降优先级。

## 19:45 查清「渠道调度模式（随机/轮询）在界面上改不了」

起因：建议把 marathon 改成 random，用户回「界面上没看到有修改轮询或者随机的地方了」。

**结论：编辑已有渠道时，两个主题都改不了 multi_key_mode——这是前端写死的，不是用户没找到。**

前端有**两个同名但语义完全不同**的 `multi_key_mode`，混淆源头就在这：

| 字段 | 取值 | 含义 |
|---|---|---|
| `formData.multi_key_mode` | `single` / `batch` / `multi_to_single` | 添加渠道时的**密钥录入方式**（表单控件） |
| `formData.multi_key_type` | `random` / `polling` | 真正的**多 key 调度模式**（存进 `channel_info.multi_key_mode`） |

关键在 `channel-form.ts`：`multi_key_type` 只在 `mode === 'multi_to_single'` 时才被
塞进 `multi_key_mode` 提交；而**编辑态 `multi_key_mode` 被硬编码成 `'single'`**（第 479 行）。

- **classic**（`EditChannelModal.jsx`）：「密钥聚合模式」Checkbox 带 `disabled={isEdit}`（2041 行），
  随机/轮询 Select 是 `{batch && multiToSingle && (...)}`（3114 行）→ 编辑时进不去；
  提交走 `API.put` 只发 `localInputs`，`multi_key_mode` 仅在创建分支带上（1865-1876 行）。
- **default**（`channel-mutate-drawer.tsx` + `channel-form.ts`）：`multiKeyMode === 'multi_to_single'`
  才渲染（3170 行）；`transformFormDataToUpdatePayload` **压根不输出该字段**（715-770 行）；
  isEditing 时还会强制 `setValue('multi_key_mode','single')`（1295 行）。

**后端其实是支持的**：`controller/channel.go:914` 的 `PatchChannel.MultiKeyMode *string`
（`PUT /api/channel/`），第 976-978 行套在 origin ChannelInfo 之上（不会丢 IsMultiKey/MultiKeySize）。
且 `multi_key_mode` 在 `controller/channel_authz.go:134` 的**非敏感字段白名单**里，
ChannelWrite 权限即可改，不需要 ChannelSensitiveWrite。
但该接口是**全量更新**，只发 `{id, multi_key_mode}` 会被 `validateChannel` 打回，得带完整字段。
→ **所以直改 SQL 最干净**：
```sql

SET channel_info = (channel_info::jsonb || jsonb_build_object('multi_key_mode','random'))::json
WHERE id = 10821;
```
（`channel_info` 是 **json 不是 jsonb**，收尾必须 `::json`。）DB 路径每次请求实时读，改完立即生效。

**顺带挖出一个真实的线上性能坑**（比缓存问题更值得关注）：

## 23:1x param_override 简化 + 限流调研 + 权重规则修正

### 1. param_override 从 920 字符压到 127 字符（实测 8/8 通过）

用户问「为什么这个参数覆盖里面的内容这么复杂」。拆解后发现**复杂度全是多余的**：

原版 4 个 operation + 8 个条件（920 字符）：
- 2 个字段（`max_tokens` / `max_completion_tokens`）× 2 个模型（glm / deepseek）
- 每个 operation 各带 `model contains` + `lt` 两个条件

**实测推翻了两条我以为必须的约束：**

- **不需要 `model` 条件**：`value` 取两个上限中较大的（384000）即可 ——
  超上限对上游只是**截断**、不报错。实测 glm 收 `max_tokens: 384000`（自身上限 131072）→ 200。
- **不需要 `lt` 条件**：该渠道只有这两个模型，无条件 set 的唯一副作用是"客户端要更小的值也被抬高"。

最终版（127 字符，2 ops，0 条件）：
```json
{"operations":[{"path":"max_tokens","mode":"set","value":384000},{"path":"max_completion_tokens","mode":"set","value":384000}]}
```

**A/B/C/D 直连验证（glm-5.3-flash）**：
| 请求 | 结果 |
|---|---|
| 只 `max_tokens: 131072` | 200 |
| 只 `max_completion_tokens: 131072` | 200 |
| 两个都 131072 | 200 |
| `max_tokens: 131072` + `max_completion_tokens: 16` | **500** |

→ **两者并存时上游取更小的那个**。所以真实流量必须两个都 set
（`buildTestRequest` 只设 `MaxTokens`，且 `dto/openai_request.go:37-38` 都是 `omitempty` 指针，
所以**只跑渠道测试的话只 set `max_tokens` 也够**）。

**教训**：最初一步步加条件试错，于是误以为"必须按模型区分 + 每个字段各带条件"。
**先用无条件最小版跑通，再按需加约束** —— 反过来的话分不清是哪一步修好的。
