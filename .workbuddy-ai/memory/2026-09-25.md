# 2026-09-25

## 调研：Drex（决策模型）能不能接进 new-api

上游 `https://drex.nace.ai`（Nace 的决策模型，与 TypeSafe Jev 线协议兼容）：

- **唯一端点 `POST /v1/systemone`**。入参 `model` + `state`（文本或 JSON）+ `questions`（三种类型：`noul` 是/否概率、`choice` 从自定标签里选、`score` 有序刻度）。
- 出参 `answers`（每题一个概率分布 + confidence）+ `usage`（`input_tokens`/`output_tokens`）+ `evaluation_time_ms` + `request_id`。
- `GET /v1/models` 存在（且不校验余额）。**无流式**（单次 JSON 返回，别传 `stream: true`）。
- 计费：只算 `usage.input_tokens`，$0.04 / 1M，输出 token 不计费；只有 200 才扣费；401/402/422/429/500/529 免费。402 = `insufficient_credit`，充值后即恢复（= new-api 的"临时自愈"语义，不该禁用渠道）。
- 注册送 $25（30 天过期，每邮箱一次，**一次性邮箱域名不给**）。

**结论：能接，但必须降级到 OpenAI 形状的入站路径，不能原生暴露 `/v1/systemone`。**

代码依据（本地 git，custom 分支 = 线上）：

1. `router/relay-router.go` 只注册固定路由（`/v1/chat/completions`、`/v1/responses`、`/v1/messages`、`/v1/embeddings`…），没有通配转发 → 直接打 `/v1/systemone` 是 404。客户端必须改用 `/v1/chat/completions`。
2. `controller/relay.go:113` 的 `helper.GetAndValidateRequest` 在进入 adaptor **之前**就把 body 反序列化进 DTO 并校验（`GetAndValidateTextRequest` 要求 `model` 非空、`/v1/chat/completions` 还要求 `messages` 非空）→ Drex 的裸 body 会 400 `field messages is required`。**必须塞一个占位 `messages`**（顺便把 `state` 文本抄进占位消息里，让 token 估算大致成比例）。
3. **逃生口 = 渠道设置 `pass_through_body_enabled`**（UI 渠道编辑抽屉里的「Pass Through Body / Pass request body directly to upstream」，见 `web/default/.../channel-mutate-drawer.tsx:4157`）。
   - `relay/compatible_handler.go:97-107`：开关打开时**跳过** `ConvertOpenAIRequest`、`RemoveDisabledFields`、param_override，直接用 `common.GetBodyStorage(c)` + `ReaderOnly(storage)` 发**原始字节**。
   - `common/gin.go:86-130` 证明 storage 存的是原始 body，`UnmarshalBodyReusable` 只是 seek 回去再读，不会改写它 → `state`/`questions` 逐字节到达上游。
4. 渠道类型二选一：
   - **type 8（自定义）**：`relay/channel/openai/adaptor.go:317-320` → `base_url` **原样使用**（只替换 `{model}`），不拼入站路径。所以 `base_url = https://drex.nace.ai/v1/systemone` 即可，最省事。代价：上游模型更新检测走 default 分支拼 `{base_url}/v1/models`（`controller/channel_upstream_update.go:394`）→ `.../systemone/v1/models` 404，得关掉该开关。
   - **type 58（高级自定义）**：`advanced_routes` 配 `/v1/chat/completions` → `/v1/systemone`（converter=none）+ `/v1/models` → `/v1/models`（该路由必须 `models` 为空、converter=none，见 `dto/channel_settings.go:347-360`）。好处是模型列表可用；注意 `model/channel_cache.go:247-268` 对 type 58 会按入站路径过滤候选，路由必须真能匹配上。
5. 响应侧 `OpenaiHandler`（`relay/channel/openai/relay-openai.go:190`）：反序列化进 `dto.OpenAITextResponse`，发现 `usage.prompt_tokens == 0` → 用估算值**覆写** `usage`，其余字段（`answers`/`evaluation_time_ms`/`request_id`）原样回传。⇒ Drex 原生的 `usage.input_tokens` 会被冲掉，要精确数字只能看 Drex 后台 CSV。
6. 计费：completion 侧没有 `choices` → 恒为 0，实际只算输入侧，方向与 Drex 的"只计输入"一致；但数值来自占位 messages 的估算，不会等于 Drex 报的 `input_tokens`。必须在 `options.ModelRatio` 里配 `drex-latest`，否则 `model_price_error`（定价是整体覆盖，不合并）。

⚠️ 未实测：Drex 是否容忍多出的顶层 `messages` 字段。其文档明确说"有若干 TypeSafe 接受的请求会被 Drex 有意返回 422"，说明它是有校验的，接入前先打一发探针。

## 调研续：社区是怎么把这类决策模型接进 Claude Code 的（关键结论）

**前提纠正：Claude Code 从来没把决策模型当"模型"接。** 网上那波来自一个 41 万播放的 YouTube 视频 "Jev will 10x your Claude Code"，最流行的误读就是"改 base_url 就行"——官方文档和社区分析都明确否掉了：Jev/Drex 没有 `/v1/chat/completions`、没有 Anthropic Messages 面，返回的是带概率的结构化答案，**没有 assistant message、没有 token 流、没有 tool call**，CLI 解析不了。

**协议不匹配的解法不是写转换层，而是"不经过模型通道"**，三条可行路线（共同点：模型通道不动，判断挂在 harness 边界上）：

1. **官方 agent skill** — `claude plugin marketplace add typesafe-ai/skills` → `claude plugin install typesafe@typesafe-ai`（Codex 用 `npx skills add typesafe-ai/skills --skill typesafe-ai`）。只**教 agent 怎么写调用**，不拦截 CLI。核心价值：让 agent 把多个问题批量塞进一次调用（TypeSafe 自测 13 问批处理 ≈ 便宜 12×、快 10×；请求预算约 32k token）。
2. **边界 hook** — PreToolUse 门禁（`jev-axi`）、工具输出剪枝（`jev-pruner`）、Stop 钩子验"完成"声明（`jev-belay`）、压缩插件。⚠️ 好的实现都 **fail-open**（判断失败/超时/无 key → exit 0 空 stdout，不冻结 CLI）。
3. **MCP 工具** — `claude mcp add jev -e TYPESAFE_API_KEY=sk-... -- npx -y @jkudish/jev-mcp`。⭐ **这就是协议桥**：工具参数是高层语义（`claims`/`candidates`/`classes`/`fields`），**由调用方 LLM 填**，MCP server 再映射成原生 `{model, state, questions}`；答案以 tool result 形式回到对话。**LLM 自己就是适配器**，所以不需要线格式转换。
4. **按轮次模型路由** — `jev-router`：在 CLI 前放回环代理，每轮调一次 Jev 只为了**选模型层级**（Fast/Balanced/Strong ↔ Haiku/Sonnet/Opus、gpt-5.6-luna/terra/sol），真正写代码的还是前沿模型。这是最常被误认为"在 Jev 上跑 Claude Code"的路径。用 `ANTHROPIC_BASE_URL` 重定向，复用 CLI 自己的登录态，fail-open。

**Drex 直接吃这套生态**：Drex 文档说与 TypeSafe Jev **线协议兼容**，TypeSafe SDK 改**三个环境变量**就能指向它 → 按 `jevwire`/`jev-mcp` 的环境变量表，就是 `TYPESAFE_BASE_URL=https://drex.nace.ai` + `TYPESAFE_API_KEY=nace_sk_...` + `JEV_MODEL=drex-latest`。

## 对上一条结论的修正（重要）

上一条"能接 new-api"要加限定，**取决于调用方是谁**：

- **自己的程序**（知道要发 `state`/`questions`）→ 能接，走 `pass_through_body_enabled`。本质等价于"把决策调用塞进一个不属于它的通道"，能用但脆（校验逼你塞占位 `messages`）。
- **OpenAI 形状的客户端**（Claude Code / Cursor / Cherry Studio / LobeChat / 任何 SDK）→ **接不了**。它们会发 `messages` 期待 `choices[].message.content`，占位 `messages` 只骗得过网关的校验，骗不过客户端的解析。理由和社区发现的一模一样。

**设计教训**：new-api 是**模型网关**，决策模型不是模型。要正经托管它，得**给它自己的原生路径**（像 APIMaster 那样卖 `jev-latest` 并暴露原生 `POST /v1/systemone`），而不是伪装成 chat completions——即新增一条独立 relay 路由 + 新 API type，而不是复用 `RelayFormatOpenAI`。
