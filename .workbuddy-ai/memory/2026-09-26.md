## ✅ 已完成：Codex Responses Lite 协议桥（commit b260bc02）

用户拍板「自己针对 gpt codex 做一层转换，因为用户不可能改模型名，且不要影响其他渠道」，
于是把上面那条「可选定制」实现了。**只在 Kite Router 线生效，其他渠道零影响。**

**新增** `relay/channel/kitedelayed/codex_lite.go` + `codex_lite_test.go` + `testdata/`；
改动 `adaptor.go`（Router 分支挂钩）与 `dto/openai_response.go`（`ResponsesOutput` 加 `Input` 字段）。

**请求侧** `hoistCodexLiteTools`：
1. `additional_tools` 项 → 提升为顶层 tools，并从 input 移除（否则变空 developer 消息）；
2. `namespace` → 展平（Lite 与 legacy 都有）；`web_search`/`local_shell` 等 chat 表达不了的**丢弃**；
3. `custom`(lark grammar) → 降级成单字符串参数 `source` 的 **function** 工具，
   并在描述前**前置显式引导**（见下）；
4. 历史项 `custom_tool_call` → `function_call`（参数包成 `{"source": "<js>"}`），
   `custom_tool_call_output` → `function_call_output`。

**响应侧**：非流式遍历 `Output`、流式用 `codexLiteStreamRewriter` 改写事件 ——
`exec` 的 function_call → `custom_tool_call`（`input` 为源码原文），
参数 delta 攒齐后在 done 时一次性按原文发出（JSON 参数被切碎后无法逐片还原）。
custom 工具名集合通过 gin context 从请求侧传给响应侧。

**三个非显然的坑（都是实测踩出来的）**
1. ⚠️ **`custom_tool_call_output` 在 relayconvert 里没有分支** → 落到默认分支变成
   `role:user` + 空 content，assistant 的 tool_calls 无人应答 → **上游直接 502**
   （症状是「第一轮能跑、第二轮必挂」）。必须归一化成 `function_call_output`。
   定位手法：把本地渠道 `base_url` 指向一个只记录 body 的假上游，直接看网关发了什么。
2. ⚠️ **降级成 function 后模型会自创 API**：实测出现过 `tools.exec({command})`、
   `Deno.Command('pwd')`。在工具描述前置一段引导（"must drive the nested tools through
   the global `tools` object, e.g. `await tools.exec_command({cmd: "pwd"})`; there is no
   Node, Deno, require, import, fetch or console"）后，模型稳定输出正确 JS。
3. ⚠️ Lite 的 `exec` 描述里含**全部嵌套工具的 TS 声明**（exec_command/apply_patch/...），
   这段描述**必须原样保留**——它是模型写 JS 的唯一依据。

**本地端到端验证（真实 Codex，模型名保持 Lite 的 `gpt-5.6-luna`）**：
```

exec   /bin/zsh -lc pwd in /private/tmp  →  /tmp
codex  /tmp
```
多轮闭环跑通，**客户端零改动**。本地渠道必须同时带生产的 `param_override`
（`max_tokens` 钳制 + `parallel_tool_calls` delete），否则第二轮会 502。
⚠️ 本地实例重启后 **cookie 失效**，管理 API 会回 `Unauthorized, not logged in`，
必须先重新登录再建渠道（否则渠道没建上，还以为改动没生效）。
⚠️ `openai/gpt-6-astra` 的 Codex 体量请求在 key #1 上会 **402 insufficient_router_balance**
（预留额度高于实际消耗），测试用更便宜的 `gpt-5.6-luna` 即可。

2. 展平过的工具调用在响应里要**补回 `namespace` 字段** —— Codex 按命名空间匹配工具注册表。
   cc-switch 的 `response_function_call_item_with_namespace` 明确产出 `{name, namespace}`；
   我的 `codexLiteToolSpec{Name,Namespace,Kind}` 就是为此从 `map[string]bool` 升级的。
3. `tool_search_output` 与 `additional_tools` 同形，同样要提升其工具声明；
4. function 工具的 `parameters` 统一规范成 `{"type":"object",...}`
   （严格上游会因 `parameters: null` 直接 400）。
另外自己测试暴露：`custom_tool_call_output` 单独出现时也要触发 input 重写。

**有意保留的差异**：cc-switch 把 namespace 展平成 `<namespace>__<name>`（64 字符 sha256 截断）
并在响应侧还原；我沿用**裸名**。理由：实测 Codex 按裸名也能匹配（exec 走通全闭环）、
当前 Codex 工具集内无同名冲突、且不改模型看到的工具名。若将来冲突，改成前缀方案即可。

**⚠️ 已知缺口**：Codex 的 `tool_search`（动态加载工具）未实现。cc-switch 用一个
`tool_search` 代理 function 工具 + 把 chat 调用还原成 `tool_search_call` 项来支持。
当前抓到的 Lite 请求里没有 tool_search（插件/MCP 工具被折进 exec 的嵌套工具表），
所以未实现；声明该工具时模型将无法搜索工具。

## ✅ 已补齐：`tool_search`（commit 279a7c95）

用户追问「tool_search 为什么没实现、什么场景用、万一用到不就报错了」——**追问是对的**。

**触发场景**（来自 cc-switch 的 v3.20.2 release notes，与 Codex 行为一致）：
Codex 依据**模型元数据 `supports_search_tool`** 决定是否把 MCP/插件工具**延迟**到
`tool_search` 之后 —— 声明 true 就只给一个搜索入口、工具本身不下发；false 就直接内联列出。
（cc-switch 曾因此踩坑：官方 catalog 给 deepseek 声明了 true，而 DeepSeek 不提供
`tool_search`，结果所有 MCP 工具被藏起来一个都调不到。）

**原先的失败模式 = 静默丢能力，不报错**：`{"type":"tool_search"}` 被当成 chat 表达不了的
条目丢弃 → 模型看不到搜索入口 → 被延迟的 MCP/插件工具**全都用不了**（不会 502）。
比报错更隐蔽。所以补了。

**实现**（镜像 cc-switch）：
- 请求侧：`{"type":"tool_search"}` → 声明 `query`/`limit` 的代理 function 工具；
  历史 `tool_search_call` → 名为 `tool_search` 的 function 调用；
  `tool_search_output` → **既提升其携带的工具、又保留成 tool 结果**
  （只提升不保留 = 搜索调用无人应答）。
- 响应侧：还原成 `tool_search_call` 项（`execution:"client"`、`arguments` 为**对象**、
  status 按事件区分 in_progress/completed）；流式下参数**仍走 `function_call_arguments.*`**，
  不像 custom 那样被吞掉。
- 顺带修 early-return 判据：只声明 tool_search 的请求原先会直接放行 → 代理工具没被声明。

**仍存缺口**：hosted `web_search` 表达不了（chat 协议里没有联网搜索能力），已写进代码注释。

**验证**：18 个单测全绿（新增 5 个覆盖 tool_search 声明/历史归一化/响应还原/流式/参数兜底），
全量回归通过，真实 codex exec 端到端复验通过。

## 💰 Kite Router 的额度模型（402 insufficient_router_balance 的完整解释）

**用户报「跑一半 402，但我账户有余额」** —— 那个 402 来自**上游 Kite Router**，

**key 池真相**：10867 的 11332 个 key 是**不同账号**（`/v1/me` 显示邮箱各异：
jason82@bestvirtualgoods.com / brent.woods@... / cynthiawoods@virtualgoods.top ...），
**每个账号只有 $5.00 welcome credit**（`/v1/credits` 可查，免费）。

**⭐ required_microusd 的公式（实测标定，2026-09-26）**：
```
required ≈ prompt_tokens × 2 × 输入价  +  max_tokens × 输出价  +  ~$0.004
```
标定证据（gpt-6-astra，$15/M 入、$75/M 出）：
- 同提示、`max_tokens` 8192→1024：required 恰好少 **$0.5376 = 7168 × $75/M** ⇒ 输出预留按 `max_tokens`

- 提示 2507→25007 token：required 增 **$0.675 = 22500 × $30/M** ⇒ 提示系数是 **输入价的 2 倍**。
- 校验：2507 提示 + 默认输出 ⇒ $0.0752+$0.6144+$0.004 = $0.694（实测 $0.6937）✅

**⇒ 一个 $5 账号能服务的提示上限（= 上下文天花板）**：
| 模型 | 输入 $/M | $5 额度可撑提示 |
|---|---|---|
| `gpt-6-astra`（含 `gpt-5-codex` 别名） | 15.0 | **146k token** |
| `gpt-5.6-sol` | 6.0 | 396k |
| `claude-opus-5` | 7.5 | 313k |
| `gpt-5.6-luna` | 0.30 | 无上限（1.05M 上下文内均可）|


## 🧩 Codex 原生压缩（compact）协议契约 —— 服务端压缩的正解

用户提出「服务端主动压缩为主、错误兜底」，我核对后发现**协议原生就有这个机制**，
不需要自定义「压缩块」。契约（全部来自官方源码/本仓库）：

- **端点**：`POST /v1/responses/compact`
  - new-api 已路由：`router/relay-router.go:104` → `RelayFormatOpenAIResponsesCompaction`；
  - `RelayModeResponsesCompact`（`relay/constant/relay_mode.go:54`），
    `controller/relay.go:51` 与 responses 共用 `relay.ResponsesHelper`；
  - DTO：`dto/openai_responses_compaction_request.go`（注释直指 codex 提交
    `53d5972`/`5d6f23a`）、`dto/openai_compaction.go`；
  - 响应 handler `relay/channel/openai/relay_responses_compact.go` 是**纯透传**
    （只解析 usage，body 原样回），所以 `output` 形状完全由 OpenAI 契约定义。
- **响应形状**：`output` 里放一个
  `{"type":"compaction","id":"cmp_...","encrypted_content":"<不透明串>"}`
  （Codex `ResponseItem::Compaction`，`codex-rs/protocol/src/models.rs:1228`，
  `#[serde(alias="compaction_summary")]`，字段 `id` + `encrypted_content`）。
- **客户端语义**：Codex 取这个 item 后 `retained.push(compaction_output)`
  （`codex-rs/core/src/compact_remote_v2.rs:529`）—— **用它替换整个历史**，
  之后每轮只带这个块。触发是 `CompactionTrigger::Auto`（由模型目录的
  `auto_compact_token_limit` 控制）+ Manual。失败会 `should_retry_with_current_model`。

**⭐ 为什么这解决了「网关侧压缩每轮重复」的反对意见**：客户端压缩后**只保留压缩块**，
所以只压缩一次，不是每轮。**「主动」的位置必须在客户端**（HTTP 请求-响应模型下服务端
无法主动发起）；服务端能做的是「被调用时执行」+「下发建议阈值」。

**⭐ 最优雅的一点**：`encrypted_content` 是**服务端生成、客户端原样回传的不透明串**
⇒ 我们可自定义内容（放摘要的 base64）。**网关保持无状态**，不需要存会话；
下一轮转换层识别 `type:"compaction"` 解码成摘要文本即可。

**⭐ 硬约束：压缩必须用便宜模型**。压缩请求本身要把完整历史发给上游 ——
155k 历史用 `luna` 压缩只需 **$0.108**，用 `astra` 要 **$5.27** ⇒ 压缩调用自己就超限，
**死锁**（要压缩的正是那个超限的上下文）。
**算总账**：155k 会话在 astra 上本来必死（$5.27>$5）；走 `luna 压缩($0.108) → astra 续跑
(~5k 摘要, $0.764)` = **$0.87** ⇒ **把 astra 的 146k 天花板真正绕过去了**。
**额度检查必须排在压缩之前**：单条输入就超限时压缩也救不了，要直接返回明确错误。

**当前状态（实测）**：
- `/v1/responses/compact` **近 7 天零调用**（全站 24h：chat 18754 / responses 357 / messages 12）
  ⇒ 是**潜在缺口**，不是正在发生的故障。
- Kite Router 线**未实现 compact**：`adaptor.go:646` 的 Router 分支只在
  `RelayModeResponses` 时生效，compact 会落到普通分支把上游 chat 响应当 compaction 响应解析
  ⇒ 形状错误。上游也**没有** `/v1/responses/compact`（OpenAPI 无）⇒ 必须用 chat 接口自建压缩。

⇒ astra 的 $4.5 线是 **258,773 字节**（≈6.5 万 token 散文 / 13 万 token 代码），不是 129,386 token。
（已回写进 `yutou-api-prod-channel-ops` skill，那条旧公式会误导排查。）

## 🔴 上线后第一个真实反馈：撞线时只报错，Codex 不自动压缩（已定位 + 已修）

用户实测报错（10867 已启用，user_id=251）：400 `context_budget_exceeded`，
且文案自相矛盾「约 258773 字节（约 64693 token），当前约 292185 字节（约 12498 token）」。

### 根因（源码级，不是闸门的问题）

**Codex 的压缩是客户端在「发请求之前」触发的，网关的 400 无法让它回头压缩。**
触发线来自模型元数据 `auto_compact_token_limit`；Codex 不认识我们的模型名 →
用 fallback 元数据（`models-manager/src/model_info.rs`）：
```rust
context_window: Some(272_000), max_context_window: Some(272_000),
auto_compact_token_limit: None,     // ← 没有阈值！
```
⇒ 它要等到 `272000×95% ≈ 25.8 万 token` 才压缩，而我们的线是 **25.8 万字节**
（≈6.5 万 token 口径）—— **晚了约 4 倍**，于是直接把超限请求发出来被闸门拒掉。
**文档 §5.1 的 4a「由客户端触发压缩」不会自动发生**，这是原设计的漏洞。

### 已修（commit 9326aae27）

1. **文案口径统一**：两个 token 数一律用 字节/4（判据本来就是字节）。原来「当前」
   那个数取自 `info.GetEstimatePromptTokens()`，而网关对 responses 请求的 token 估算
   **只统计部分字段**（工具调用密集的 Codex 请求严重低估，实测 23 字节/token）。
   metadata 加 `bytes_per_token_used`。补了回归测试。
2. **渠道级闸门逃生阀**：`settings.kite_router_budget_gate_disabled=true`
   → 该渠道完全跳过闸门（含压缩调用的预算检查），行为退回改动之前，≤60s 生效。
   10867 已启用，这个开关是必须的应急手段。
