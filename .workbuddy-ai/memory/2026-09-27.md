## 跨渠道 key 禁停一致性（同一天第二个提交 `0df1f71e9`）
- 用户追问「如何保证两个渠道 key 的禁启用一致」，暴露了更深一层：
  **key 禁停状态是按渠道存的**（`channels.channel_info.multi_key_status_list`），
  而 `AutoDisableChannelKeys(channelID, …)` / `EnableChannelKeys(channelID, …)` /
  管理 API 全是**单渠道**语义 → 同一个上游账号挂在两个渠道上时，写入天然会分叉。
- 上一版只修好了「读」（URL 不再 404），**写仍然是渠道级的** —— 谁扫出来的只写谁。
- 本版改成：把本轮所有渠道的禁用判定并成 `mergedDisableReasons` 再**逐渠道下发**。
  `AutoDisableChannelKeys` 只遍历渠道自己持有的 key 并查表，所以并集对不持有它的渠道
  是无害空操作 ⇒ 幂等。跳过 `auto_ban=0` 的渠道。401 熔断闸门改成记录 `guardedKeys`
  并全局剔除，否则闸门会被兄弟渠道的并集绕过。
- 单测：一个渠道探测正常 + 一个渠道全线失败（base_url 指向 `127.0.0.1:1`），
  低余额 key 必须在两个渠道都被摘掉。
- ⚠️ **仍未解决的方向：没有任何东西会「重新启用」Kite key**。
  `EnableChannelKeys` 全仓库只被 `tokenharbor_key_scan.go` 调用一次（Kite 无调用方）。
  所以一旦某个 key 在某个渠道被摘掉而余额回升，就是**永久单向漂移**。真实可达路径：
  真实流量在 Router 线撞到 `402 required_microusd > balance`（就是 09-26 那批）→
  `handlerMultiKeyUpdate` 只禁用 10867 的那一份 → 任务下一轮探到余额正常 → 10821 保持启用、
  10867 永久禁用 ⇒ Router 线静默少一个可用 key。要做成 TokenHarbor 那样「状态=最近一次探测」
  得让任务同时具备 re-enable 能力，需要先定策略（滞回阈值 / 是否碰 status=2 的手动禁用）。

## 10821 / 10867 错误归因（23:50–次日 00:10）
- **口径**：必须按 `request_id` 聚合（单条日志是「每次上游尝试」，6 次重试会把失败率放大 6 倍）。
  近 24h：10821 = 211 请求 / 7 失败 = **3.3%**（avg_attempts 1.00）；
  10867 = 249 请求 / 34 失败 = **13.7%**（avg_attempts 1.13）；近 6h 10867 升到 **18.3%**。
- **10867 三条根因（全部直连复现）**：
  1. ⭐ **上游 Kite Router 边缘 60s 硬超时**：同一 key 直连
     `https://delayed-inference.prod.gokite.ai/v1/chat/completions` 打长输出，

     ⇒ Router 是**同步接口**，任何生成 >60s 的请求**必然** 504，是结构性上限，网关侧无解。
     （对照：Marathon 线的 504 是**我们自己的** 5 分钟 `pollTimeout`，25 次全部正好 300s。）
