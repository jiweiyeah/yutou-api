改法：走管理 API（`PUT /api/option/`，root 的**裸** access_token + `New-Api-User: <userId>`），

+26.9s  event: message_start / content_block_start / ping
+46.9s  : PING
+66.9s  : PING
+86.9s  : PING
+87.5s  event: content_block_delta

⇒ 修复前正是这 60 秒会触发 `client_gone`。注意**首个 ping 要等一个 interval**（20s），

## 诊断：10856 crusoecloud 的 `503 No capacity available, retry later`（只读，未改动任何配置）

**结论：与 key 额度无关，是上游 Crusoe 共享推理池的容量过载。**

- 563 个 key **全部 status=1**，`multi_key_disabled_reason` 为空 → 网关没摘过任何 key。
- 近 7 天错误码：ok 6405 / **503 559** / 400 61（其中 60 条是「客户端给纯文本模型发图」，
  即既有的 multimodal 400）/ 403 16 / 504 6 / 502 3 / 500 1。
  **无 402、无 429、无任何 quota/credit 字样** —— Crusoe 超额会回 **429**，一条都没有。
- 503 分散在 **313 个不同 key** 上，且**同一 key 既有成功又有 503**（idx=6 → 13 ok / 6 个 503）
  → 不是 key 级故障形态。
- 直连抽样 5 个 key × 3 次（含日志里那条 503 用的 **idx=541**）：**14×200 + 1×000**（连接抖动）。
  即刚报 503 的 key 立刻就能 200。

**模型级差异是关键证据**（同渠道同批 key，近 7 天）：

| 模型 | 503 率 |
|---|---|
| `z-ai/glm-5.3-flash` | **15.72%** (529/3353) |
| `z-ai/glm-5.3` | **0.23%** (7/2970) |
| `moonshotai/kimi-k2.6` | 12.04% |
| `deepseek/deepseek-v4-pro` | 2.55% |

差 **68 倍** ⇒ Crusoe serverless 按 **project × model** 独立计限额与伸缩，flash 承载的
多租户流量远大于 GLM-5.3，更容易撞共享池上限。**不是渠道配置问题。**

**官方定义**（`docs.crusoecloud.com/serverless-inference/rate-limits`）：
`429` = 你的项目超了该模型 TPM/RPM；**`503` = 你在限额之内，但共享端点负载过高**。
官方称 503 是瞬态的、恢复比 429 还快，建议**指数退避**（1/2/4/8s + 抖动，上限 30–60s）。

**用户实际体验**（按 `request_id` 聚合，近 24h，不能用单条日志算）：
2174 客户端请求 → 2076 最终成功 = **95.5%**，avg_attempts 1.15、max 6。
（单次上游尝试 15.72% 失败，被 `RetryTimes=5` 的重试吸收掉大部分。）

**可干预项 / 不可干预项**：
- ❌ 别加 `AutomaticDisableKeywords` —— 503 是瞬态的，加了会**永久误杀健康 key**
  （同 408 超时误杀 tokenharbor 那次的教训）。
- ⚠️ 网关重试是**无退避**立即重试，与官方建议相反；共享池过载时反而加剧争抢，
  也容易出现 `use_channel` 6 段全 503。想改需动 `relay` 重试逻辑。
- ⚠️ `z-ai/glm-5.3-flash` 目前**只有 10856 一个渠道在服务** → **无法分流**。已核实其余 6 个
  都是 `status=2`（手动禁用），且其中 3 个的 key 池已被大面积自动摘除：
  10819 tokenrouter / 10836 bitdeer = key 级 **408 超时**（「响应时间 206.15s 超过阈值 60.00s」，
  即 `ChannelDisableThreshold=60` 误杀）；10844 braintrust = key 级 403。
  ⇒ **「启用其他渠道分流」这条建议现实可行性很低**，短期内只能靠 Crusoe 侧提额/预留容量。
- ℹ️ 503 ∈ `AutomaticRetryStatusCodes`（414–503 区间）→ 会重试，但**不触发自动禁用**（默认只认 401）。

**可复用查询**：`substring(content from 'status_code=(\d+)')` 提状态码；
`(regexp_match(other,'"multi_key_index":(\d+)'))[1]` 定位用了池里第几个 key；
`other` 里 `error_code` 是上游错误体带出来的（`capacity_unavailable` **不在本地代码里**，
`grep` 无命中，别去代码里找）。

### ☠️ 这个修复第一次上线静默失效了（重要教训）

## 【修复】流式 responses 漏计 reasoning delta 导致输出 token 不计费

commit `f8b1bd636`，新增 `relay/channel/openai/relay_responses_test.go`（3 个用例）。

**先证伪再修**：按「路径 × `end_reason`」统计零 usage 占比，确认是 responses 特有缺陷——
`/v1/chat/completions` 的 `client_gone` 225 次**全部**有 usage，`/v1/messages` 6/6 也有，
而 `/v1/responses` 的 `client_gone` **2/2 全是零 usage**。

**根因**：usage 只在流末尾的 `response.completed` 里；客户端断开就拿不到，只能靠
`responseTextBuilder` 本地估算。而 responses handler 只累积 `response.output_text.delta`，
**漏了 `response.reasoning_text.delta`** → 输出全在 reasoning 里的模型（Atria 就是）
在断流时 builder 恒空 → `ct=0`，且第二段兜底 `pt==0 && ct!=0` 因此不触发 → 两个值都停在 0。

**修法**：把 delta 集合对齐 chat 侧（`ProcessStreamResponse` 是基准：content + reasoning +
tool 参数），补齐 `reasoning_text.delta` / `reasoning_summary_text.delta` /
`function_call_arguments.delta`。

**这是同一 bug 类的第二次出现**：`helper.go:112` 那次是 `/v1/messages` 走 `RelayModeUnknown`
没按 chat 解析，注释里已写明「否则 builder 恒空…completion_tokens 会被算成 0」。
**排查这类问题先看 `end_reason`，再对照 chat 路径的 builder 累积了哪些字段。**

**抓真实事件名**：`curl -sN … | grep -o '^event: .*' | sort | uniq -c | sort -rn`
（atria 实测：output_text.delta ×56、reasoning_text.delta ×6、completed ×1）。

**验证时的关键边界（我第一次测错了）**：`relay/helper/stream_scanner.go:298-301` **故意**在
`client_gone` 时立刻关闭上游 `resp.Body`（注释：避免为已放弃的请求继续消费上游 token），
所以 builder 里只有断开**之前**收到的 delta。**断开太早（第一个 delta 之前）时 ct=0 是正确行为。**

实测对照（同模型同 prompt，只改断开字节数）：

| 断开时机 | pt | ct | 结论 |
|---|---|---|---|
| 读 300 字节 | 0 | 0 | **正确**（连 `response.created` 都没读完，无任何 delta） |
| 读 3000 字节 | 12 | **7** | ✅ 修复后能估算 |
| 读 6000 字节 | 12 | **49** | ✅ 同上 |

判据：修复后这类行 `content` 里**不再出现**「上游没有返回计费信息，无法扣费」。
**教训：复现"断流"类问题时，断开时机本身就是要控制的变量——先让数据流进来再断。**

### 补修：prompt tokens 必须**无条件**兜底（commit `f2bc916a3`）

`f8b1bd636` 只补了 reasoning delta 的累积，兜底仍是 `if pt == 0 && ct != 0`——**ct 为 0 时
连 prompt 都不计费**。断开太早（无任何 delta）时两个值都停在 0，整条请求零计费。

**基准是 chat 路径的 `service.ResponseText2Usage`（`service/usage_helpr.go:22`）**：
`usage.PromptTokens = promptTokens` 是**无条件赋值**，在 `relay-openai.go:179`
`if !containStreamUsage` 分支调用。responses 侧多了个 `&& ct != 0`，就是缺口来源。

修法：`pt == 0` 即视为上游未上报 usage，直接 `info.GetEstimatePromptTokens()` 兜底。

**生产验证**（部署后）：`head -c 300` 断开 → `pt=12, ct=0, client_gone`，
且 `content` **为空**（「无法扣费」文案消失）。修复前同场景是 `pt=0 ct=0` + 报错文案。

**通用方法**：排查"某路径不计费"，**先找同类成熟路径（chat）把两边兜底逐行对齐**，
别只看本路径自己是否自洽。
