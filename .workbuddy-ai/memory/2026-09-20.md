## 归因：渠道 10844（braintrust）deepseek/deepseek-v4.1-flash 的 429

用户问「这个限制到底是什么」。直连探测 + 日志定量，结论确定。

### 结论
- 429 来自 Braintrust 侧 **provider 级 token 配额**：`x-ratelimit-limit-tokens: 1000000`
  （1M tokens/分钟）+ `x-ratelimit-limit-requests: 120`（120 请求/分钟）。
- **瓶颈是 TPM 不是 RPM**：429 响应头 `remaining-tokens: 0` 而 `remaining-requests: 61`。
- **配额跨 key 共享**：8 个不同 Braintrust org 的 key 返回完全相同的 remaining 数字
  （0 / 61）→ 加 key 无用。
- **实测消耗 1,013,100 TPM（101.3%）**，越界即 429。近 24h 该模型 19574 请求 / 7529 成功
  → 失败率 61.5%。
- **根因是单请求 prompt 太大**：`deepseek-v4.1-flash` 平均 prompt_tokens = **251,156**
  （p50 277k / p95 298k），completion 仅 1.1k。每次请求吃掉 1/4 的分钟配额，
  约 4 次/分钟就打满 1M。

### 端点分流（关键区分）
| 模型 | 端点 | 结果 |
|---|---|---|
| `deepseek-v4.1-flash` | `x-bt-error-origin: openai`（passthrough） | 429，共享 1M TPM 池 |
| `deepseek-v4-flash-0731` | `x-bt-used-endpoint: BRAINTRUST_NATIVE_INFERENCE_DEEPSEEK` | 200 |
| `glm-5.3-flash` | `x-bt-used-endpoint: BRAINTRUST_NATIVE_INFERENCE_GLM` | 200 |

→ 只有 v4.1-flash 没有原生端点，回落到受限的 openai 兼容 provider。

### 该模型承载渠道
只有 10844 在服务（10848 verboo / 10854 apmix 均 status=2）。无法分流。

### 顺带发现
- 渠道 10844 有 324 个 key，其中 **index 0–139 已被自动禁用**
  （126 个 403 + 14 个 401，时间 09-14 20:00 ~ 09-18 03:06），
  `multi_key_disabled_reason` 在 `channel_info` 里。剩余可用 184 个。
- `deepseek-v4.1-flash` 实际上游模型名是 `deepseek-v4.1-flash`（去掉 provider 前缀），
  靠 `channels.model_mapping` 映射。直连探测必须用映射后的名字，
  否则会拿到误导性的 404 `No provider found for ...`。

### 缓解方向
1. 客户端压缩 prompt（唯一根治手段，25 万 tokens/次是根因）
2. 降低重试次数：429 在 `AutomaticRetryStatusCodes` 里，`RetryTimes=5` → 6 次无退避重试，
   抢占 RPM 配额且全部失败
3. 在 Braintrust 侧给该 provider 提额，或自建 provider 绕过共享池
4. 加 key 无效（已验证共享配额）

### ☠️ 关键结论：prompt caching **不省配额**
成功请求的 `other` 里有 `cache_tokens` 字段（`service/text_quota.go:210` 赋值，
`logs.prompt_tokens` 是**含缓存的总量**，计费时才 `-= CacheTokens`）。

实测最近 1h：230 次成功，平均 `prompt_tokens = 250,991`，平均 `cache_tokens = 242,547`
→ **缓存命中率 95.8%**。

但：
- **按总量口径**：4 次/分 × 250,991 = **1,003,964 TPM** → 恰好打满 1M ✅ 与 429 吻合
- 按计费口径（cache_ratio 0.5）：4 × (8,444 + 242,547×0.5) ≈ **518,870 TPM** → 不该 429 ❌

→ **Braintrust 的 `x-ratelimit-limit-tokens` 按「总输入 token」计，缓存命中部分照样占配额。**
**缓存只省钱（cache_ratio 0.5），完全不省 TPM。** 试图"关缓存"只会让计费更贵、配额不变。

## ☠️ 重大修正：不是「配额被打满」，而是「双通道随机回落」

前面基于日志得出的「所有 key 共享配额、请求太大打满 1M」**结论不完整**。
直连逐 key 探测后发现了真正机制：

### 现象：同一个 key、同一秒，请求随机走两条完全不同的通道
```
idx=165  [200 ep=BRAINTRUST_NATIVE_INFERENCE_DEEPSEEK] [429 og=openai] [200 ...NATIVE_DEEPSEEK]
idx=150  [200 ...NATIVE_DEEPSEEK] [429 og=openai] [200 ...NATIVE_DEEPSEEK]
idx=160  [429 og=openai] [429 og=openai] [200 ...NATIVE_DEEPSEEK]
```
- **成功时** → `x-bt-used-endpoint: BRAINTRUST_NATIVE_INFERENCE_DEEPSEEK`（原生端点，**无限流头**）
- **失败时** → `x-bt-error-origin: openai`（passthrough provider，1M TPM 已满）

→ **Braintrust 网关对 `deepseek-v4.1-flash` 做「原生端点优先 + passthrough 兜底」的随机分发。**
429 只发生在**回落到 passthrough** 的那部分请求上。

### 排除了三个假设
| 假设 | 实验 | 结论 |
|---|---|---|
| 换 model slug 能绕开 | 试 5 种写法 | ❌ 只有 `deepseek-v4.1-flash` 有效，且必走 openai |
| 某些 key 走独立通道 | 抽样 37 个 key | ❌ 200/429 随机交错，非 key 差异 |
| 并发高导致回落 | 并发 8 vs 串行 8（大请求） | ❌ 并发 62.5% 反而高于串行 25% |

**回落是平台侧随机行为，与 key、并发、频率无关，网关侧无法影响。**

### ★ 但「请求越大越容易回落」——这是唯一可干预的杠杆
| 场景 | 单次尝试成功率 |
|---|---|
| 直连小请求（10 tokens）× 12 | **83%** |
| 直连大请求（2.5 万 tokens）× 8 | **62.5%** |
| **生产大请求（27 万 tokens）** | **约 7%** |

反推：客户端请求级最终成功率 35.2%、平均尝试 4.96 次、最大 6 次（用满 `RetryTimes=5`）
→ `(1-p)^6 = 65%` → **单次尝试成功率仅 p ≈ 7%**。

```sql
-- 算「用户实际体验」的标准查询（按 request_id 聚合，比看单条日志准得多）
WITH reqs AS (
  SELECT request_id, bool_or(type=2) AS any_ok, count(*) AS attempts
  FROM logs WHERE channel_id=<id> AND model_name='<model>'
    AND created_at > extract(epoch from now())::bigint - 3600
    AND coalesce(request_id,'') <> ''
  GROUP BY 1
)
SELECT count(*) AS client_reqs, count(*) FILTER (WHERE any_ok) AS finally_ok,
       round(100.0*count(*) FILTER (WHERE any_ok)/count(*),1) AS ok_pct,
       round(avg(attempts),2) AS avg_attempts, max(attempts) FROM reqs;
```

### 结论：网关侧无法做有效压缩（逐项排除）
| 手段 | 结论 |
|---|---|
| prompt caching | ❌ 只省钱不省配额（且不提高原生端点命中率） |
| `prune_objects` 按 role 删消息 | ⚠️ 能减小请求，但删 tool 消息会打断 agent 工具链 |
| 按位置裁剪（保留最后 N 条） | ❌ 不支持；`invert` 只能表达"保留匹配项"，无法表达窗口 |
| 按 token 数触发条件 | ❌ 上下文无 token 数；`messages.#` 只给消息**条数** |
| 网关侧摘要/压缩 | ❌ 无此功能 |
| 加 key | ❌ 无效（已证） |
| 令牌级限流 | ❌ `tokens` 表无 rpm/tpm 字段 |

**→ 唯一真正有效的是「增加供给」（加新渠道 / Braintrust 提额 / 在 org 内自建 provider），
或降级到走原生端点的模型。**

## ★ 修正：多 key 渠道的自动禁用是 **key 级**的，不是渠道级（同日，推翻上面第 2 条）

读代码确认的完整链路：

```
controller/relay.go:253   processChannelError（每次失败后立刻调用，在 shouldRetry 之前）
  └ NewChannelError(..., usingKey = ContextKeyChannelKey, ...)   ← usingKey 在
     middleware/distributor.go:480 设置 = 本次实际选中的那个 key
  └ service.ShouldDisableChannel(err) && AutoBan
     └ 非 auto-disable-error → service.DisableChannel() → DisableChannelUntil(until=0)
        └ model.UpdateChannelStatus(channelId, usingKey, AutoDisabled, reason)
           └ 多 key 渠道 → handlerMultiKeyUpdate（model/channel.go:650-703）
              ├ 按 usingKey 在 keys 里找 index → 只写 MultiKeyStatusList[index]=3 ✅ key 级
              ├ usingKey 非空但找不到 → 直接 return，什么都不改
              ├ usingKey 为空 → 才改渠道整体 status（如 channel-billing.go:476 "余额不足"）
              └ 仅当 hasEnabledMultiKey==false（全军覆没）→ 渠道整体 AutoDisabled
```

**顺手拿到的通用事实**（已写进 skill `yutou-api-prod-channel-ops` 第 15 条）：
