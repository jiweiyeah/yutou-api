### ④ 渠道测试选 messages 端点报 converter 错（2026-10-11，非配置问题）

现象：UI 渠道测试选 messages 端点测 `anthropic/claude-opus-4.7`，报
`converter "anthropic_messages_to_openai_chat_completions" does not support OpenAI chat completions requests`；
选 chat/completions 正常。

链路（已逐行核对 + 实测 `Path2RelayMode("/v1/messages") == RelayModeUnknown(0)`）：

1. `controller/channel-test.go:311` 用 `switch info.RelayMode` 选转换入口；
2. `relay/constant/relay_mode.go` 的 RelayMode 枚举**没有 messages/Claude 这一档**，
   Gemini 虽有 `RelayModeGemini(35)` 但 switch 里也没 case；
3. → 落 `default:`（`:375-385`）调 `adaptor.ConvertOpenAIRequest`，测试体由
   `buildTestRequest`（`:738`）对 Anthropic/Gemini/OpenAI 一律构造成 `*dto.GeneralOpenAIRequest`；
4. 58 型 adaptor 的 `resolve()` 按**请求路径**解析 converter → `/v1/messages` 得到
   `anthropic_messages_to_openai_chat_completions`，与 OpenAI chat 入口不匹配 → 报错。

⇒ **测试工具缺陷**。真实请求走 `controller.Relay(c, RelayFormatClaude)` → `relay.ClaudeHelper`
→ `claude_handler.go:165 ConvertClaudeRequest`，入口与 converter 匹配，正常。
结论：58 型渠道用 UI 测试只能验 chat/completions 和 responses；messages / gemini 会误报。

### ⑦ relaykit / tokenkit 重构调研（2026-10-11）

上游把协议转换层拆成**独立 Go module** `relaykit`（`github.com/QuantumNous/new-api/relaykit`，
独立 go.mod / Go 1.25.1，运行时只依赖 uuid、lo、gjson、sjson，独立 tag `relaykit/vX.Y.Z`，
`go get` 可直接安装）。动机见 `86ac0f774`（2026-07-27，#6369），分 Phase：
- Phase 0：先加 **golden snapshot matrix** 钉住每条 (from,to) 路由的字节级输出 + 边界守卫测试
- Phase 1：converter 签名从 `*gin.Context` + `*relaycommon.RelayInfo` → `context.Context` +
  `convmeta.Meta` 接口；宿主设置走 `convmeta.Options` 快照，转换层不再全局读 model_setting/reasoning
- Phase 2：`dto.Request.IsStream` 改收 `*http.Request`；抽零依赖 `kitutil`；dto/types/relayconvert
  不再 import common；宿主能力反向注入（`SetMediaResolver` / `kitutil.SetCodec` / `SetLogging`）

⇒ 转换层零 gin/gorm/redis/setting 依赖，可独立测试、独立发布、嵌进其他网关。

**规模对比**：上游 `relaykit/` **159 文件** vs 我们 `service/relayconvert/` **43 文件**。
我们缺：`convmeta`、`kitutil`、`reasoning`(7)、`reasonmap`、`toolconv`(7)、`convdiag`、
citations、gemini grounding、hosted stream、Claude↔Responses 双向转换、testdata golden 矩阵(24)。

**功能优化要点**：四协议全矩阵互转（带 good/fair/discouraged 质量评级）；Responses 的 custom tool /
namespace 工具降级为 function tool 并用 `ResponsesToolState` 记录、响应时还原；托管 web search 按
目标协议重编码 + 按厂商上报计费；Gemini grounding 按查询计费；推理设置用 `ReasoningConversionState`
跨步骤传递并返回诊断（`claude_max_tokens_raised` 等）；统一 `dto.Usage` + `BillingUsage` 保留上游原始
usage 与来源协议；流式 `ResponseStreamState` + `FinalizeStreamResponse` + `FailResponsesStream`。

**另一个独立 module `tokenkit`**（`bb28f2cca`）：修 token 估算对 agent 流量的严重低估 ——
原先 Claude tool definitions / Responses function calls 及输出 / Chat assistant tool calls /
Gemini system instructions+function calls+tools **完全没进计数器**，Chat tool schemas 按 Go map
语法计数、Claude tool results 当转义 JSON。用 54 个真实 Claude Code/Codex 会话窗口对照上游 usage：
**prompt 估算偏低 31–93%**，Claude/Gemini 的 completion fallback 偏低约 90%。现按 tokenizer 分族
拟合权重（Claude 4.7 前后同文本差约 30%），prompt 估算偏差 <1%、平均误差 3–4%。

**与 58 型渠道直接相关**：`69a500298`（2026-09-15）给 advanced custom 渠道加了**按路由的
pass-through**（我们目前只有渠道级 `pass_through_body_enabled`），前端编辑器同步加 UI（+122 行）。
