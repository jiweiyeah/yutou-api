## 修复：把 deepseek_free_tier_recovery 改造成 TokenHarbor key 池主动巡检（commit a17c5812c，已部署 latest）

### 关键发现：TokenHarbor 有零成本探测端点

`GET https://tokenharbor.ai/v1/models` —— 有效 key → **200**，被吊销 → **401**。
（`/v1/credits` **不存在**，返回 404 HTML。）这让"全量探测整个 key 池"变得可行。

上游错误语义（`logs.type=5` 归类，近 30 天）：**401** invalid/revoked key（真死）、
**402** "We can't serve our models on this account right now"（账号级临时限制，会自愈）、
**403** "Free-model consent has changed" / "Verify your email"（需人工操作）、
**429** "Too many failed authentication attempts"（限流）、500/400 与 key 无关。

### 改动

- 新增 `service/tokenharbor_key_scan.go`：全量探测并**重建**状态（2xx→启用 / 401→禁用 /
  其他→禁用），并发 16（`TOKENHARBOR_SCAN_CONCURRENCY`）；
  `TOKENHARBOR_DISABLE_MAX_RATIO`（默认 0.5）熔断 —— 单轮要禁用的比例超阈值就一个都不禁。
  渠道按 **base_url host** 匹配（`tokenharbor.ai` 及子域），不按 type。
- 新增 `model.EnableChannelKeys`（对称于 `AutoDisableChannelKeys`）、`model.GetChannelsWithKeys`。
- `deepSeekFreeTierRecoveryHandler` 同时跑 DeepSeek 恢复 + TokenHarbor 扫描，
  **result 结构变为 `{"deepseek":{...},"tokenharbor":{...}}`**（旧格式已废弃）。
- 新增 `POST /api/system-task/free-tier-recovery` 手动触发（走 `service.EnqueueSystemTask`）。
- interval 默认 5→**360** 分钟；线上 `/opt/new-api/docker-compose.yml` 也从 10 改成 360。
- 单测 `service/tokenharbor_key_scan_test.go`，含"上游全挂时熔断不禁用"的用例。

### 执行结果

- 部署：`gh workflow run custom-deploy.yml -f ref=custom -f tag=latest -f platforms=linux/amd64 -f deploy=true`，约 5 分钟。
- 先 SQL 清空 10831 的 `multi_key_status_list`/`reason`/`time`/`until` → 59 个禁用 key 全部启用。
- 触发任务：**tokenharbor 只有 3778 个 key**（别跟 marathon 的 10525 搞混），32 秒跑完，
  `keys_checked=3778, request_errors=0, disable_guard_tripped=false`。
- 判定结果：**52 个 401 + 3 个 403 = 55 个禁用**；
  **7 个此前因 408 超时被误杀的 key 全部恢复正常并保持启用** —— 正是"先全启用、再让任务筛一遍"的目标。

### 坑

- `channels` 表**没有 `updated_time` 列**（只有 `created_time`），UPDATE 带上它会整笔回滚。
- `multi_key_status_list` 的 **index 是 `GetKeys()` 数组下标**（按 `\n` 分割），不是 key 本身。
- 部署脚本只 sed `image:` 行，**不动 env**；env 改动要靠 `up -d` 重建容器才生效，
  借部署这次重启一起生效最省事（重启后缓存从 DB 重建，省掉等 60s 同步窗口）。

## 跟进修复：网络层失败不再误杀 key（commit 6b531a2a4）

首轮上线后的复测暴露一个真实缺陷：**探测请求根本没到达上游时（DNS/连接/超时），
原实现把它当成"上游说这个 key 不行"并禁用了它**。

发现过程：直连复测 7 个恢复的 key，`idx=1933` 返回 `HTTP 000`（curl 连接层失败）；
紧接着连测 3 次全部 **200 / 0.25s** —— 是网络抖动，不是死 key。
按原逻辑这个 key 会被误禁用，且要等一整个 interval（6 小时）才恢复。

改法：判定从三路扩到**四路**，新增 `indeterminate`（没有响应 → **不动状态**）。
同时把探测 URL 和 HTTP client 从"每 key 解析一次"提到"**每渠道解析一次**"，
配错的 base_url 记入新的 `channel_errors` 并跳过该渠道，不会表现成整个池子全坏。
summary 里 `request_errors` 字段被 `indeterminate_keys` + `channel_errors` 取代。

新增两个单测：`...LeavesStateAloneWhenProbesNeverReachUpstream`（transport 恒失败 →
状态列表保持为空）和 `...ReportsBadBaseURLAsChannelError`（host 匹配但无 scheme → 
`channel_errors=1`、`keys_checked=0`）。

> 测这个坏 URL 场景时踩了个小坑：`tokenharbor.ai/v1`（无 scheme）的 `Hostname()` 是空，
> `IsTokenHarborChannel` 直接返回 false，渠道根本不会被匹配，测试意图不成立。
> 要构造"host 匹配但构造不出探测 URL"，得用 scheme-relative 形式 `//tokenharbor.ai/v1`。

### 验证方法：A/B 对照，而不是"没新建行"

"没新建行"是假阳性 —— 任务本来没到 interval 就不该建行。正确做法是把 interval 临时压到 1 分钟
制造"已到期"，再对照开关：
- A 面 `ENABLED=false` + `INTERVAL=1`：95s（调度器 tick 15s，约 6 轮）内 **0 新建行**（仍 119 条 / max id 9384）。
- B 面 `ENABLED=true` + `INTERVAL=1`：同窗口内建出 **2 行**（id 9391 @10:58:09、9392 @10:59:09，
  均为 `channels:7, keys_scanned:0`）→ 证明调度器活着、任务确实到期、**开关就是那个闸门**。
- 收尾删掉临时 INTERVAL 行，`diff` 备份确认只剩 1 行；容器 healthy，`/api/status` 正常。

> 遗留：id 9391/9392 这两条是 A/B 测试产物，留在表里（未删），未来审计看到别误判。

### 坑

- **`system_tasks.result` 列类型是 text**，不是 jsonb。`result->>'x'` 报
  `operator does not exist: text ->> unknown`；且**有行的 result 是空串**，
  `array_agg(result::jsonb ...)` 会整条报 `invalid input syntax for type json`。
  一律 `NULLIF(result,'')::jsonb->>'x'`。
- `ScheduledSystemTaskHandler.Enabled()` 返回 false → `runSystemTaskScheduler`
  （`service/system_task.go:270`）在建行前就 `continue`，不是"建了行再跳过"。
- 调度器 tick **15s**（`systemTaskSchedulerInterval`）。

## 用户报 `messages is required and must be a non-empty array`（deepseek/deepseek-v4-flash）

- 错误是**上游 400**（`status_code=400, ...invalid_request_error`），不是网关自产
  （网关自产文案是 `field messages is required`，`relay/helper/valid_request.go:333`）。
- 根因：**用户走的是 `/v1/responses`（Responses API）**，body 是 `input` + `max_output_tokens`；
  该模型启用的渠道 #10831 tokenharbor / #10850 atria-asi 都是 type 8 且
  base_url 钉死在 `.../v1/chat/completions`，只认 chat completions → 上游找不到 messages。
- 数据（24h）：/v1/responses → v4-flash 188(10831) + 173(10850) = 361 次**全失败**；
  全量日志 v4-flash + /v1/responses = 1538 次、**0 成功**；mimo-v2.5 267 次同样 0 成功。
  同渠道同模型 /v1/chat/completions 7333 次成功。首次出现 09-05 14:48，近 24h 6 个用户。
- **`other.request_path`** 是定位这类问题的关键字段：`NULLIF(other,'')::jsonb->>'request_path'`
  （`other` 是 text，成功/失败日志都写）。1220/1220 条该错误 request_path 都是 `/v1/responses`。
- 只有 **type 58** 会按 request_path 过滤（`model/channel_cache.go:247`，非 58 一律放行）
  → type 8 渠道会接到自己不支持的端点请求。
