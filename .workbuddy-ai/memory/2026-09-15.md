## 分析渠道 10844（braintrust）已禁用 key 的 token 消耗

### 数据来源与方法

- 日志表 `logs.other -> admin_info -> multi_key_index` 记录每个请求命中的 key 下标，
  覆盖率 100%（48297/48297）。这是唯一的归因字段，`logs` 表本身没有 key index 列。
- 该字段在 `service/log_info_generate.go:97-101` 写入，仅当 `ContextKeyChannelIsMultiKey` 为真。
- `other` 是 text 列（非 json），用 `(regexp_match(other, '"multi_key_index":(\d+)'))[1]::int` 提取最稳，
  避免非法 JSON 导致 `::json` 转换报错。

### 关键陷阱：key 池替换会重置索引语义

`multi_key_index` 是**数组下标**，不是 key 的稳定标识。渠道 10844 的 key 池在
**09-13 02:00 被整体重建**（838 个 key → 7 个），之后尾部追加扩容：
21（09-13 17:00）→ 35（09-14 20:00）→ 61（09-15 03:00）→ 64（09-15 13:00）→ 76（09-15 18:00）。

判定方法：按小时聚合 `max(multi_key_index)`，出现断崖式下跌即为重建点。

- 不做窗口限定直接统计 → 得到 880,920,594 tokens（**错误**，混入了旧池的 key）
- 限定 09-13 02:00 之后 → 833,385,763 tokens（**正确**）

### 结论（限定当前 key 池生命周期内）

- 已禁用 64 个 key（idx 0–63，全部 403 触发）：833,385,763 tokens，quota 115,479,898 ≈ $230.96
- 仍启用 12 个 key（idx 64–75）：16,159,397 tokens，quota 1,047,891 ≈ $2.10
- 禁用后竞态逃逸：446,048 tokens（0.05%），13 条日志，均在禁用后 1–165 秒内，非逻辑失效
- 两批禁用：idx 0–20 于 09-14 20:00 集体禁用；idx 21–63 于 09-15 12:21–16:42 陆续禁用
- quota 换算：`common/constants.go` 中 `QuotaPerUnit = 500000`（500000 quota = $1）

明细导出：`.workbuddy-ai/outputs/channel_10844_disabled_keys_tokens.csv`（64 行）

### 单 key 产出量（同批次 64 个 key）

- 累计产出：min 3.89M / p25 8.55M / **中位 12.65M** / p75 16.63M / max 52.72M，均值 13.02M tokens
- 请求数：中位 318，均值 296
- quota：中位 1,600,142（≈$3.20），均值 1,804,373（≈$3.61）
- 存活时长：中位 18.5 小时（区间 3.0–42.0）

**关键结论：单 key 没有固定产出上限，产出 = 渠道总流量 ÷ 活跃 key 数。**

- 反证 1：存活 42 小时的 idx 0–6 产出 8.2M–13.3M，**低于**存活 18.5 小时的中位数
- 反证 2：09-15 14:00（41 key，总 93.7M）与 16:00（12 key，总 95.4M）总流量相近，
  key 数少 3.4 倍 → 单 key 产出高 3.5 倍（2.29M → 7.95M/小时）
- 实测单 key 速率区间：0.13M–7.95M tokens/小时

**403 成因判断**：不是"跑满额度"。第一批 idx 0–20 在 09-14 20:00 的 **197 秒内集体 403**，
符合上游批量失效特征；第二批 idx 21–63 于 09-15 12:21–16:42 陆续倒下。
注意 403 也非 429/402，更像账号层面封禁而非限流或欠费。

### 复用要点

统计多 key 渠道历史消耗前，**必须先验证 key 池是否发生过整体替换**，否则归因错误。
评估"单 key 承载量"时，要按小时同时输出「活跃 key 数」和「单 key 产出」，
只看累计值会把流量波动误读成 key 上限。

## 容量测算与模式选择（09-15 追加）

### 实测基线

- 单 key 平均产出 16.08M tokens（今天报废的 43 个 key 均值），中位 12.65M
- 单 key 平均寿命 17.7 小时（中位）
- 09-15 消耗 577.8M tokens / 20 小时，峰值小时 95.4M（16:00，仅 12 个 key 在扛）
- **交叉验证**：43 个 key 累计产出 691.6M ≈ 同时段渠道总流量 690.7M（误差 0.1%），基线可信

### 容量结论

- 常备可用 key **50 个**（40 个即可扛住 60–95M/小时）
- 每天补货 **约 70 个**（50 × 24 ÷ 17.7），分批错时启用，每 4–6 小时一批

### 模式选择：保持 random

- random 与 polling 都在渠道级锁内执行（`model/channel.go:244-284`），无性能差异
- 今天 14,278 请求下 random 分配已足够均匀（42 key 窗口 CV 27.4%，差异主要来自加入时间）
- **关键**：polling 严格等量 → 所有 key 同步归零；random 有方差 → 错峰失效
- polling 的 `MultiKeyPollingIndex` 不落库：`model/channel.go:263` 的
  `CacheUpdateChannel(channel)` 被注释掉，`SaveChannelInfo()` 仅在 `!MemoryCacheEnabled` 时执行，
  生产开内存缓存时重启即重置
- 注意：若失效纯属上游批量封禁（idx 0–20 在 197 秒内集体 403 属此类），两种模式无差别

## 429 限速根因定位（09-15 21:45 追加）

### 直接探测上游得到的硬事实

用渠道里的 key 直连 `https://gateway.braintrust.dev/v1/chat/completions` 看响应头，比读日志有效得多：

- 429 响应头：`x-ratelimit-limit-tokens: 1000000`、`x-ratelimit-remaining-tokens: 0`、
  `x-ratelimit-limit-requests: 120`、`x-ratelimit-remaining-requests: 61`、`x-bt-error-origin: openai`
- 429 body 只有 `{"error":"Rate limit exceeded"}`，**没有 retry-after / reset 头**
- 结论：**触发维度是 TPM 而不是 RPM**（tokens 归零、requests 还剩 61）；
  错误来自 Braintrust 背后的 OpenAI 上游，不是 Braintrust 自身限流

### 令牌桶是整组 key 共享的

用 idx 64 / 70 / 75 三个不同 key 连续请求，同一秒内返回**完全相同**的
`remaining-requests: 61` + `remaining-tokens: 0`。若按 key 独立计数，三个 key 不可能一致。
→ 1,000,000 TPM 的桶归整组 key 共享，**堆 key 不会扩容**。

### 403 的真相（修正今天早些时候的判断）

探测已禁用 key（idx 0/5/21/33/63）得到：
`403 Braintrust gateway error: Braintrust model 'deepseek-v4.1-flash' unauthorized, insufficient credit balance`，
且 `x-bt-error-origin: braintrust`。
→ 是**额度/信用不足**，不是账号封禁。关键字 `insufficient credit` 命中 `AutomaticDisableKeywords` 才被自动禁用。
→ 且 `MultiKeyDisabledUntil` 为空 → `model/channel.go:956` 直接 return，**403 禁用不会自动恢复，必须人工重新启用**。

### 我们的表现（09-15 21:00 档）

- 交付吞吐 1.0–1.6M tokens/分钟，正好压在 1M TPM 天花板上；21 点档 429 1493 次 vs 成功 281 次
- 单请求平均 152K tokens（峰值 490K）→ 1M TPM ÷ 152K ≈ **6.6 请求/分钟** 理论上限，
  实测成功 6.9/分钟，完全吻合
- 客户端需求 ≈ 1136 请求/小时 ≈ 18.9/分钟 → 需求是容量的 **~2.9 倍**
- 重试放大：2092 次上游 429 对应 489 个客户端请求 = **4.28 倍**
  （`RetryTimes=5`，`AutomaticRetryStatusCodes` 含 `414-503` 覆盖 429，且**重试之间没有任何退避**）
- 客户端最终失败率 23.1%（1136 请求 / 262 失败）
- 12 个可用 key 全部被均匀打到 429（每个 258–291 次/6 小时）
- `deepseek/deepseek-v4.1-flash` 一个模型独占 30.05M/30 分钟 ≈ 1.0M tokens/分钟，**单模型吃满全部预算**

### 排查手法（可复用）

判断上游限流维度，**不要只看日志里的 status_code**。直连上游拿响应头能看到
limit/remaining 的分维度计数，一眼区分 TPM 还是 RPM；`x-*` 自定义头（如 `x-bt-error-origin`）
还能告诉你错误是平台自己产生的还是透传自更上游。日志里 `showBodyWhenFail=false` 会丢掉错误体。

### 修正（09-15 22:00）：限流责任方是 Braintrust 原生推理端点，不是我们的账号

用户指出「不同 key 都是不同账号的」，这与我先前"整组 key 共享一个桶"的解释冲突。补测后定位到真正原因：

**成功响应的响应头给出了责任方**：

```
x-bt-used-endpoint: BRAINTRUST_NATIVE_INFERENCE_DEEPSEEK   ← 完成请求的凭证
x-bt-secrets-scope: org
x-bt-cached: MISS
```

对比 `glm-5.3-flash` 是 `BRAINTRUST_NATIVE_INFERENCE_GLM`。
→ 这些模型走的是 **Braintrust 自己的原生推理**，不是我们配的 provider key（BYOK 的凭证名会是
`OPENAI_API_KEY` 这种用户自命名）。所以 1M TPM / 120 RPM 是 **Braintrust 原生推理上游的容量**，
在账号层之上，与我们有几个 key、几个账号无关。这同时解释了：
- 76 个 key 确实是 76 个不同账号（64 个各自 `403 insufficient credit balance`）
- 但不同账号打同一模型拿到的 `x-ratelimit-remaining-*` 完全相同

**另一个关键对比实验**：同一个 key 打 `braintrust/gpt-6-astra` / `braintrust/gpt-5.6-luna` /
`glm-5.3-flash` / `kimi-k3` / `deepseek-v4-flash-0731` **全部 200 且不带任何 x-ratelimit 头**，
只有 `deepseek-v4.1-flash` 429。→ 瓶颈只在这一条模型路由上。

**官方文档核实**：Braintrust 文档**没有**任何网关 LLM 的 TPM/RPM 数值。
`docs/api-reference#rate-limits` 讲的是 api.braintrust.dev 平台 API，不覆盖 gateway；
`docs/deploy/gateway` 只把 429 列为可触发 provider failover 的上游错误；
`docs/plans-and-limits#system-limits` 只有 Function executions 10000/10s、query timeout 30s 等。
→ **1,000,000 TPM / 120 RPM 是实测值，不是官方解读**，汇报时必须标明。

**官方文档里真正有用的机制**（`docs/deploy/gateway`）：
- `x-bt-error-origin`：braintrust 或 provider 名，区分错误来源
- `x-bt-used-endpoint` / `x-bt-failover-from` / `x-bt-failover-to`：确认故障转移
- `x-bt-fallback-providers`（请求头，逗号分隔的凭证名）：**429 会触发 provider failover**，
  前提是在 Braintrust 里配了组织级/项目级 AI provider 凭证
- `x-bt-use-cache` / `x-bt-cache-ttl`：网关响应缓存
- failover 不重试网关鉴权错误/校验错误，以及 429 以外的 provider 客户端错误

**落地要点**：渠道表有 `header_override`（JSON，`relay/channel/api_request.go:processHeaderOverride`），
所以可以直接下发 `x-bt-fallback-providers`，不用改代码。

## 重试策略为什么"只能全局改"（09-15 22:15 追加）

用户指出无法只降低 429 的重试次数。核实后确认**属实**，相关旋钮全是全局的：

- `common.RetryTimes`（`common/constants.go:157`）是全局变量，只由全局 option `RetryTimes` 赋值（`model/option.go:521`）
- `AutomaticRetryStatusCodeRanges`（`setting/operation_setting/status_code_ranges.go:21`）全局，只由全局
  option `AutomaticRetryStatusCodes` 赋值
- `alwaysSkipRetryStatusCodes`（硬编码 `{504,524}`）、`alwaysSkipRetryCodes`（硬编码 `{BadResponseBody}`）
  **不可配置**
- `shouldRetry`（`controller/relay.go:346-376`）只看状态码/错误码，**完全不看渠道**
- `dto.ChannelSettings` / `ChannelOtherSettings`（`dto/channel_settings.go:13-57`）**没有任何重试字段**
- `header_override` 只改上游请求头，与重试无关

→ 要做渠道级 429 重试策略，必须改代码。改动很小：`ChannelSettings` 加字段，
`shouldRetry` 读 `relayInfo.ChannelMeta.ChannelSetting`（该字段已存在，
见 `relay/common/relay_info.go:63-81`，调用点在 `controller/relay.go:255`，`relayInfo` 已在作用域内）。

### 重试的实际收益与分布（决定全局改动的代价）

- 全站 24h：撞过 429 的客户端请求 7313 个，**74.7% 最终成功**；没撞 429 的 35947 个，95.1% 成功
  → 429 重试确实在起作用，不是纯浪费，全局摘掉有真实代价
- 429 高度集中：10844 = 12709 次，10838（b.ai，type 8）= 7229 次，两者占 **98.1%**
- **`deepseek/deepseek-v4.1-flash` 有第二条渠道：10831（tokenharbor，type 8）**，
  09-15 13:42 被人工停用（`other_info.status_reason = manual operation`），
  3025 个 key 中 46 个已 401（`Invalid or revoked API key`），最后日志是 09:45 的 500
  `upstream error: do request failed`。换一批有效 key 后启用，可同时解决分流和"重试无意义"两个问题。
- **重试必然回到同一渠道**：`RetryParam`（`service/channel_select.go:14-21`）里**没有"排除已试过渠道"的字段**，
  所以对只有一个可用渠道的模型，6 次尝试全打在同一个渠道上（日志 `use_channel: ["10844"×6]` 为证）。
  这是"放大 4.28 倍但成功率不涨"的根因。
