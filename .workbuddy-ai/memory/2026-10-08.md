## 生产故障：整机 hang（2026-10-07 23:35 北京时间）

**现象**：new-api 服务中断，用户从控制台重启服务器（boot -1 → boot 0，中断 31 分钟）。

**根因**：宿主机 CPU 严重争抢（steal），实例在负载高峰期被彻底饿死，系统失去响应。

**关键证据**：
- `/proc/stat` 累计 **steal=34.4%**；瞬时采样 7.0%~41.7%（4 核 Xeon Gold 6138 @2.00GHz）
- idle 57% 的情况下仍有 34% steal → 是宿主机主动抢占，不是本机负载导致
- boot -1 有 5 次时钟异常：`clocksource: Long readout interval` ×3（时钟跳跃 1.34s / 4.69s / 9.39s）、`hrtimer: interrupt took 112625804 ns`（中断延迟 112ms）→ VM 被完全暂停的铁证
- `wa=0.0`、PSI io/memory 全为 0 → **排除磁盘 IO 与内存**
- 容器 ExitCode=0、OOMKilled=false、内存仅用 100MB → 排除 OOM / 进程崩溃
- `last -x` 无 shutdown 记录 + journal 文件 truncated → 硬复位（非优雅关机）
- 时间线：15:18:30 UTC journald 停写 → 15:35:45 UTC dockerd 停写 → 之后全部静默 → 16:06:51 重启

**排除的误判（重要，别再踩）**：
- ⚠️ postgres `checkpoint complete: write=35~79s` **不是**磁盘慢的证据 —— 那是 PG `checkpoint_completion_target` 主动限速的设计行为；重启后第一条 checkpoint 是 `write=0.181s` 正好印证。dd 实测顺序写 **87.9 MB/s**、顺序读 121 MB/s，磁盘完全正常。
- ⚠️ syslog 在 15:18:30 后"安静"**不等于**系统挂死 —— 该机应用日志走容器 stdout，syslog 本来就稀疏（14:28→15:17 之间也空了 49 分钟）。判断挂死要看**容器日志**的断点。

**次要隐患（与本次无关，待修）**：
- 无 `/etc/docker/daemon.json` → 容器日志无轮转，new-api json.log 已 **425MB**
- journal 占 **1.8G**，`journald.conf` 是空的（无 SystemMaxUse 限制）
- 容器内存限额合计 **4.2G > 物理 3.9G**（new-api 2.8G + pg 0.9G + redis 0.5G）；swap 是 `/swapfile` 2G
- 根分区挂 `discard`（ext4 在线 TRIM）且 `fstrim.timer enabled`，低性能云盘上建议去掉 discard 改定期 fstrim
- 内核已在 10-07 06:46 升到 5.15.0-198（本次重启后才生效）

**待办**：让用户查腾讯云控制台 10-07 22:00–00:10 的 CPU 监控曲线与事件中心；建议换**独享型（标准型 S5/S6）**实例。

## 监控方案调研：cron-job.org + GitHub Actions（2026-10-08）

**结论：可以配合，但 GitHub Actions 原生 `schedule` 不能用，而且它在本场景里其实没有位置。**

- **cron-job.org 免费版**：**60 秒最小间隔**、**30 秒执行超时**、任务数不限（fair use）、完全免费。
  job 支持**自定义 header / POST body** → 能调 GitHub API（`workflow_dispatch`）。
  2026-09-29 起通知渠道支持 email + **webhook**（投递重试 3 次、每次超时 20s）。
- ❌ **cron-job.org 算不了腾讯云 TC3-HMAC-SHA256 签名** → **不能直接调 `RebootInstances`**，必须靠中间执行体。
- ❌ **GitHub Actions 原生 `schedule` 是「低优先级队列」**：实测延迟 **±10~60 分钟**，高峰可能直接跳过
  → 做不到「1~2 分钟发现」。改用外部 `workflow_dispatch` 触发则精度 ±1 秒，但每次要启动 runner
  （10~30s）+ 可能排队，总延迟 30~60s。
- ⚠️ **额度**：private repo 免费 2000 分钟/月。若用「cron-job.org 每 5 分钟触发一次」模式
  ≈ 4320~8640 分钟/月 → **必超**；要么用 public repo（无限，但 60 天无活动 schedule 会被自动禁用），
  要么改成「仅故障时才触发」。
- ⚠️ cron-job.org 里存 GitHub PAT 是明文的 → 用 fine-grained PAT，只给目标 repo 的 `Actions: write`。

**推荐架构**：cron-job.org 只做**外部探测 + 失败告警**（它的强项，1 分钟发现），
重启交给**常驻执行体** —— 腾讯云 **SCF**（角色授权免密钥）或 **Cloudflare Worker**
（已有 CF 基建，WebCrypto 算 TC3 签名）。**GitHub Actions 在这个链路里是多余的**（启动慢 + 烧额度 + 原生定时不准）。

### cron-job.org REST API（2026-10-08 调研，文档 https://docs.cron-job.org/rest-api.html）

- Endpoint `https://api.cron-job.org/`，认证 `Authorization: Bearer <key>`，**限额 100 请求/天**（支持者 5000）。
- `PUT /jobs` 建 job（body `{"job": DetailedJob}`，只有 `url` 必填）；`PATCH /jobs/{id}` 改；`GET /jobs` 列；`DELETE /jobs/{id}` 删。
- ⚠️ **通知渠道（Notification Channel）本身无法通过 API 创建** —— 文档只有 `selectedChannels` 引用 ID，没有建渠道的端点。
  **渠道 0 = 内置账号邮箱**。
  ⭐ **巧办法**：创建 job 时**省略 `mode`/`selectedChannels`** = all channels（发给账号下所有渠道）
  → 只需在 Console 手动建 1 个 webhook 渠道，API 建 job 时省略该字段即可自动关联。
- 关键字段：`schedule.minutes:[-1]` = 每分钟；`schedule.timezone` 可设 `Asia/Shanghai`；`requestMethod:0` = GET；
  `requestTimeout` 秒（-1 = 默认 30s）；`saveResponses:true` 保存响应体便于排查。
- `notification`：`onFailure`、**`onFailureCount`（≥1，设 2 可防单次抖动误报）**、`onSuccess`（恢复通知）、
  **`onDisable`（job 被自动禁用时通知 —— 必开，因为连续失败 25 次会禁用）**。
- `JobStatus` 枚举：1=OK / 2=DNS 失败 / 3=连不上 / 4=HTTP 错误 / 5=超时 / **10=challenge page（能识别 CF 挑战页）**。
- ⚠️ **用户提供的 API 密钥返回 401**（含/不含末尾 `=`、带/不带 Content-Type 都试过）→ 待用户重新核对
  （Console → Settings → API；注意 `0`/`O`、`1`/`l` 易混淆，建议用复制按钮）。
- ✅ **飞书 webhook 已验证可用**：`curl` 发文本消息返回 `{"StatusCode":0,"StatusMessage":"success"}`。
