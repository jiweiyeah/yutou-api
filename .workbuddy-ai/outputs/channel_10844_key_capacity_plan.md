## 三、运维动作

- **常备可用 key：50 个**。今天 40 个即可扛住 60–95M/小时，50 个留出余量。
- **每天补货约 70 个**（50 × 24 ÷ 17.7）。
- **分批错时启用**：每 4–6 小时一批、每批 12–18 个。同时启用会让它们同时失效。

## 四、模式选择：保持 random

结论：**维持 `multi_key_mode = random`**（当前配置）。

理由：

1. 今天 14,278 次请求下 random 分配已足够均匀——13:00–16:00 窗口 42 个 key 的消耗 CV 为
   27.4%，且该差异主要来自各 key 加入时间不同，不是分配不均。
2. **失效时刻的分布比均匀度更重要**。random 的个体方差让 key 错峰失效；polling 严格等量，
   会让所有 key 在同一时刻到达上限、集体归零。
3. polling 是有状态模式，且索引不落库：`CacheUpdateChannel(channel)` 在
   `model/channel.go:263` 被注释掉，`SaveChannelInfo()` 只在 `!MemoryCacheEnabled` 时执行。
   生产开内存缓存时索引仅存于内存，重启即重置。
4. random 对新追加的 key 立即均等分配，补货响应更快。

代码位置：`model/channel.go:244-284`（`GetNextEnabledKey`）。两种模式都在渠道级锁内执行，
不存在性能差异。

**前提说明**：若 key 失效纯属上游批量封禁（今天 idx 0–20 在 197 秒内集体 403 即属此类），
两种模式表现相同；但只要存在额度耗尽型失效，polling 的同步归零风险就是实打实的。
在失效机制尚未完全确认前，random 是更稳的默认选择。
